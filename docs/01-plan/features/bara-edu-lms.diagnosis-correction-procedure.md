## 0. 지금 시스템에서 할 수 있는 것 (2026-11-26 코드 기준)

| 화면 | 볼 수 있는 것 | 할 수 있는 것 | 접속 기록 |
|---|---|---|---|
| `/admin/selfcheck` 진단 결과 목록 | 이름 원문, 휴대전화·이메일은 마스킹. 회원/비회원 필터, 추천 단계 필터. **검색 기능 없음** | "개인정보 보기"(5분짜리 서명 토큰)로 한 건의 연락처 원문 보기 | 원문 보기 성공 시 `조회`, `진단 결과 연락처 열람(<id>)`. 기록에 실패하면 원문을 보여 주지 않아요 |
| `/admin/selfcheck/[id]` 진단 결과 상세 | 이름·휴대전화·이메일 원문, 6영역 점수, 30문항 원응답, 회원이면 회원 상세 링크 | 보기만 가능 | 열 때 `조회`, `진단 결과 상세(<id>)`. 기록에 실패하면 원문을 보여 주지 않고 안내만 보여요(구현됨 2026-11-26, 8장 R5) |
| `/admin/selfcheck/leads` 강사과정 문의 | 이름·문의 내용 원문, 연락처는 마스킹 | 연락처 원문 보기, 상태 전환(신규→연락함→종료), 메모 수정 | 원문 보기만 `조회`로 기록. 상태 전환·메모 수정도 `수정`으로 기록해요(`강사과정 문의 <id> fields=...`, 값 없음. 구현됨 2026-11-26, 8장 R4) |
| `/admin/members/[id]` 회원 상세 | 회원의 자가진단 결과 목록은 **안 보여요** | 이름·연락처 수정(`profiles`만, 11-26 배포) | `정보수정` |

정리하면:
- **열람**: 관리자 화면으로 가능해요(기록이 남아요).
- **마스킹 해제**: 목록에서 한 건씩 가능해요(기록이 남아요).
- **정정·삭제**: 진단 결과와 강사과정 문의 모두 **관리자 화면에 기능이 없어요.** 그래서 이 문서의 정정·삭제는 전부 5.2절의 DB 직접 수정으로 해요.
- **결과 확인 코드(`access_token`)로 찾기**: 관리자 화면에는 코드가 안 보여요. 코드로 찾으려면 DB 조회가 필요해요(5.2절 A).

알아 둘 DB 동작:
- 비회원 결과(`user_id is null`)는 진단일로부터 90일이 지나면 매일 도는 `purge_unclaimed_diagnosis_pii()`가 `respondent_name, phone, email, certificate_level, utm_*`를 null로 비워요. 행과 점수는 남아요. 이 함수는 이름·휴대전화·이메일 중 하나라도 남은 행을 대상으로 해요(구현됨 2026-11-26, 패치 `api/db/patches/2026-11-26-privacy-followups.sql` 운영 적용 뒤부터. 적용 전까지는 `respondent_name is not null`인 행만이라 8장 R2가 남아 있어요).
- 강사과정 문의는 접수일로부터 1년이 지나면 `purge_old_diagnosis_leads()`가 행을 삭제해요.
- 회원이 탈퇴하면 연결된 결과의 이름·연락처·자격 수준이 null이 되고, 그 회원의 `user_id`가 붙은 문의는 삭제돼요(`api/src/auth/withdraw.ts`).
- 진단 결과 행을 지우면 `diagnosis_answers`(30문항)도 함께 지워지고, 그 결과를 가리키던 문의의 `result_id`는 null이 돼요.
- `admin_access_logs`는 관리자도 고치거나 지울 수 없고, 1년이 지난 기록만 자동으로 지워져요.

## 1. 적용 범위

### 1.1 대상 데이터

| 구분 | 테이블·컬럼 | 식별 방법 | 정정 대상 항목 |
|---|---|---|---|
| 회원에게 연결된 결과 | `diagnosis_results` 중 `user_id`가 있는 행 | `user_id` | `respondent_name`, `phone`, `email` |
| 비회원 결과 | `diagnosis_results` 중 `user_id is null`인 행 | `access_token`(결과 확인 코드) 또는 제출 때 적은 연락처 | `respondent_name`, `phone`, `email` |
| 강사과정 문의 | `diagnosis_leads` | 문의 행 `id`, `result_id`, (있으면) `user_id` | `name`, `contact`, 그리고 개인정보가 들어 있으면 `message`, `admin_note` |

- 회원 프로필(`profiles`)의 이름·연락처 정정은 이 문서 대상이 아니에요. 관리자 회원 상세의 "이름·연락처 수정" 기능을 써요.
- 진단 결과의 **이름·연락처는 응답 당시 값**이라서 프로필을 고쳐도 따라 바뀌지 않아요(정의서 6장). 회원이 둘 다 고쳐 달라고 하면 프로필은 화면으로, 진단 결과는 이 문서 절차로 따로 처리해요.
- 점수·추천 단계·30문항 응답은 정정 대상이 아니에요(4장 표 마지막 줄).

### 1.2 정정 요청과 삭제 요청 구분

| 요청 | 뜻 | 처리 결과 |
|---|---|---|
| 정정 | "이름(연락처)이 틀리게 들어가 있어요, 고쳐 주세요" | 지정한 항목만 새 값으로 바꿔요. 행은 남아요 |
| 삭제 | "제 진단 기록(문의)을 지워 주세요", "연락처를 지워 주세요" | 진단 결과·문의 **행 전체를 지워요.** 항목 일부만 비우지 않아요(8장 R2 때문) |

요청자가 무엇을 원하는지 분명하지 않으면 2장 스크립트로 한 번 더 물어요. 열람·처리정지 요청은 이 문서 범위가 아니에요. 들어오면 개인정보 보호책임자(대표)에게 넘겨요.

## 2. 접수 경로와 응대 스크립트

접수 경로는 처리방침 제9조의 고객센터예요.
- 전화: 고객센터 번호(처리방침 제9조)
- 이메일: info@ylia.io

접수하면 바로 처리 대장(부록 A)에 접수번호를 매겨요. 형식은 `DC-YYYYMMDD-NN`(예: `DC-20261127-01`)이에요. **기한은 접수한 날부터 세요**(6장).

### 2.1 전화 응대

1. 요청 확인
   > "도형심리 자가진단 기록에 있는 정보를 고치거나 지우고 싶으신 거죠? 고치실 건가요, 지우실 건가요?"
2. 회원 여부 확인
   > "바라 평생교육원 회원이세요? 진단할 때 로그인한 상태였는지 기억나세요?"
3. 본인 확인(3장). 회원이면:
   > "본인 확인을 위해 가입하신 이메일 주소를 말씀해 주세요."
   
   비회원이면:
   > "결과 화면 주소(결과 링크)를 info@ylia.io로 보내 주시겠어요? 링크가 없으시면, 진단할 때 적은 연락처로 저희가 다시 연락드려서 확인할게요."
4. 고칠 내용 받기(정정만)
   > "어떤 항목을 어떻게 고치면 될까요?"
   
   새 값은 통화 중에 종이에 적지 말고 처리 담당자에게 바로 전달해요(7.3절).
5. 마무리
   > "확인 후 처리하고, 결과를 [가입 이메일 / 확인한 연락처]로 알려 드릴게요. 늦어도 열흘 안에 알려 드려요."

선택 안내(요청자가 회원이고 프로필 이름을 고치는 전화일 때만):
> "자가진단을 하신 적이 있으면, 그때 적은 이름이 따로 남아 있어요. 그것도 같이 고쳐 드릴까요?"

비회원이 정정을 원할 때 함께 안내(4장):
> "로그인하지 않고 하신 진단은 이름과 연락처가 진단일로부터 90일이 지나면 자동으로 지워져요. 상담 연락이 필요 없으시면 지금 바로 지워 드릴 수도 있어요."

### 2.2 이메일 응대

받으면 바로 보내요.
> 제목: [바라 평생교육원] 개인정보 요청을 받았어요
>
> 안녕하세요, 바라 평생교육원이에요.
> 보내 주신 요청을 [접수일]에 받았어요(접수번호 DC-…).
> 본인 확인을 위해 아래 중 하나를 알려 주세요.
> - 회원이시면: 가입하신 이메일 주소에서 이 메일에 답장해 주세요.
> - 회원이 아니시면: 진단 결과 화면 주소(결과 링크)를 보내 주세요. 링크가 없으시면 진단할 때 적은 연락처를 알려 주세요. 그 연락처로 저희가 다시 확인할게요.
> 확인되면 처리하고, 늦어도 [접수일+10일]까지 결과를 알려 드릴게요.

### 2.3 응대할 때 하지 말 것

- 본인 확인 전에는 "기록이 있어요/없어요"를 말하지 않아요. 기록이 있는지 없는지도 개인정보예요.
- 확인 전에 요청자에게 저장된 이름·연락처를 읽어 주지 않아요. 요청자가 말한 값과 맞는지만 확인해요.
- 처리 중인 문의 건은 고쳐 달라는 연락처로 상담 연락을 하지 않아요(처리방침 제6조 제3항).

## 3. 본인 확인

근거: 개인정보 보호법 시행령 제46조 제1항은 정정·삭제 요구를 받으면 요구한 사람이 본인이거나 정당한 대리인인지 확인하라고 정해요. 확인 방법은 정하지 않아요. 아래 방법이 충분한지는 8장 L2에서 검토해요.

| 대상 | 정정 | 삭제 |
|---|---|---|
| 회원 연결 결과 | 요청자가 말한 이메일이 `profiles.email`(가입 이메일)과 같아야 해요. 처리 후 결과를 **가입 이메일로** 보내서 진짜 주인이 알 수 있게 해요(정의서 Q2와 같은 기준) | 가입 이메일에서 **답장**을 받아야 해요. 지우면 되돌릴 수 없어서 정정보다 강하게 확인해요 |
| 비회원 결과 | ① 결과 링크(코드)를 보내 오고, 요청자가 말한 진단 당시 이름이 저장된 이름과 같아야 해요. 또는 ② 저장된 연락처로 **회사가 먼저** 연락해서(저장된 번호로 전화, 저장된 이메일로 메일) 요청 사실을 확인해요 | 정정과 같아요 |
| 강사과정 문의 | ① 문의의 `user_id`가 있으면 회원 기준. ② 없으면 저장된 `contact`로 회사가 먼저 연락해서 확인. ③ 연결된 진단 결과의 결과 링크 | 정정과 같아요 |
| 대리인 | 위임장과 위임한 사람의 본인 확인(위 방법)이 모두 있어야 해요(처리방침 제6조 제5항) | 같아요 |

- 걸려 온 전화번호(발신 번호)만으로는 확인으로 보지 않아요. 저장된 번호로 **회사가 다시 걸어서** 확인해요.
- 연락처 자체가 틀리게 저장된 경우(오타 등)는 ②번 방법을 쓸 수 없어요. 결과 링크로 확인해요.
- 비회원 결과는 90일이 지났으면 이름·연락처가 이미 없어서 ②번을 못 써요. 결과 링크로만 확인할 수 있어요.
- **확인하지 못하면 처리하지 않아요.** 6.3절의 거절 통지를 보내고 대장에 `거절(본인 확인 불가)`로 남겨요.
- 확인에 쓴 정보는 대장에 **방법 이름만** 적어요(`가입이메일일치`, `가입이메일답장`, `결과코드+이름`, `저장연락처회신`, `위임장`). 이메일 주소나 코드 값은 적지 않아요.

## 4. 처리 방법 결정표

| 상황 | 고를 것 | 이유·안내 |
|---|---|---|
| 회원 결과, 이름·연락처가 틀림 | **정정** | 회원 결과는 탈퇴할 때까지 보관하므로 맞는 값으로 고쳐요 |
| 회원 결과, 기록을 지우고 싶음 | **삭제**(행 전체) | 마이페이지 "자가진단내역"에서도 사라진다고 미리 말해요 |
| 회원, 계정과 기록을 전부 지우고 싶음 | **회원 탈퇴 안내** | 탈퇴하면 진단 결과의 이름·연락처는 비워지고 문의는 지워져요. 점수 행까지 지우길 원하면 탈퇴 후 결과 행 **삭제**를 이어서 해요 |
| 비회원 결과, 90일 전, 상담 연락을 원함 | **정정** | 상담 연결 목적이 아직 살아 있어요 |
| 비회원 결과, 90일 전, 상담 연락이 필요 없음 | **삭제를 권해요** | 어차피 90일 뒤 이름·연락처가 지워져요. 지금 지우는 쪽이 최소수집 원칙에 맞아요. 요청자가 그래도 정정을 원하면 정정해요 |
| 비회원 결과, 결과를 계속 보고 싶음 | **계정 연결 후 처리** | 요청자가 직접 로그인한 뒤 결과 링크에서 "연결하기"를 눌러요(회사가 DB로 연결하지 않아요). 연결되면 회원 결과가 되어 **탈퇴할 때까지 보관**된다고 꼭 말해요. 그 뒤 정정은 회원 기준으로 확인하고 처리해요 |
| 비회원 결과, 90일이 지남 | 이름·연락처는 **이미 없어요** | "이미 지워졌어요"라고 알려요. 결과 링크로 확인된 요청자가 점수 기록까지 지우길 원하면 **삭제**해요 |
| 강사과정 문의, 신규·연락함 상태, 연락처가 틀림 | **정정** | 상담을 이어 가야 해서 맞는 연락처가 필요해요 |
| 강사과정 문의, 종료 상태 | **삭제를 권해요** | 상담이 끝나서 남겨 둘 이유가 약해요 |
| 강사과정 문의, 지워 달라고 함 | **삭제**(행 전체) | 상태와 상관없이 지워요 |
| 진단 결과를 지우는데 연결된 문의가 있음 | 문의도 지울지 **물어봐요** | 결과를 지워도 문의는 남아요(`result_id`만 null이 돼요) |
| 점수·추천 단계·문항 응답을 고쳐 달라고 함 | **정정하지 않아요** | 응답한 그대로 계산한 기록이라 잘못된 정보가 아니에요. 삭제나 다시 진단하기를 안내하고, 6.3절의 일부 거절 통지를 보내요(8장 L4) |
| 이름만 지우고 연락처는 남겨 달라고 함(또는 그 반대) | 정정으로 처리할 수 있지만 **이름은 비우지 않아요** | 패치 적용 전에는 이름이 비면 90일 자동 파기 대상에서 빠져서 연락처가 영원히 남아요(8장 R2). 패치 적용 뒤에는 막히지 않지만 이 절차의 스크립트 검사는 그대로 두고, 이름을 지우려면 행 삭제로 처리해요 |

## 5. 실행 절차

### 5.1 관리자 화면으로 할 수 있는 것

정정·삭제 자체는 화면으로 할 수 없어요(0장). 화면은 아래 일에만 써요. 모두 접속 기록이 자동으로 남아요.
- 대상 찾기: 비회원 연락처로 찾을 때는 `/admin/selfcheck`에서 "비회원" 필터와 날짜로 좁힌 뒤 "개인정보 보기"로 한 건씩 확인해요.
- 본인 확인: 요청자가 말한 값과 저장된 값이 같은지 상세 화면에서 확인해요.
- 정정 후 결과 확인(5.4절).
- 문의를 지우기 전까지 상태를 그대로 두고, 처리 중에는 그 문의로 상담 연락을 하지 않아요.

결과 링크(코드)로 찾을 때와 회원 `user_id`로 찾을 때는 화면에 방법이 없어서 5.2절 A의 조회를 써요.

### 5.2 DB 직접 수정

운영 패치 관례(`docs/superpowers/plans/2026-11-24-cutover-operator-access-log.md`)를 따라요.
- WAS에서 Node `pg` 스크립트로 실행해요. 기존 운영 패치를 실행한 위치와 방법(앱 계정 `bara_edu_app`, `DATABASE_URL`은 WAS의 API 환경 파일) 그대로 써요. 접속 정보는 화면과 대화에 출력하지 않아요.
- 한 트랜잭션 안에서 `begin; set local role bara_edu_service; … ; commit` 순서로 해요.
- 접속 기록 insert는 **변경과 같은 트랜잭션** 안에서 해요. insert가 실패하면 변경도 롤백돼요.
- `bara_edu_service`는 테이블 소유자라서 RLS를 거치지 않아요. 그래서 접속 기록의 `admin_id = auth.uid()` 정책도 적용되지 않아요. **`admin_id`를 직접 정확히 넣어야 해요.**

#### 값 다루기 규칙 (정정할 때)

- 새 값(이름·연락처)은 **스크립트 파일, 명령줄, 대화, 운영자 접근 기록, 처리 대장 어디에도 쓰지 않아요.**
- 처리 관리자가 WAS에서 직접 입력 파일 `~/bara-edu-ops/<접수번호>.json`(권한 0600)을 만들어요. 예: `{"respondent_name": "…", "phone": "…"}`. 스크립트가 이 파일을 읽고, 성공·실패와 상관없이 끝나면 지워요.
- 대화형 도구(Claude Code 등)가 실행을 맡을 때도 입력 파일은 사람이 직접 만들어요. 그러면 값이 대화 기록에 남지 않아요.
- 스크립트는 값을 출력하지 않아요. 오류가 나도 `code`와 `message`만 출력하고 `detail`(행 값이 들어갈 수 있음)은 출력하지 않아요.
- 형식은 제출할 때와 같게 앞뒤 공백만 지워요(`app/actions/diagnosis.ts`도 trim만 해요).
- 삭제는 값이 필요 없어서 입력 파일을 만들지 않아요.

#### A. 대상 찾기·확인 (값을 출력하지 않는 조회)

```sql
-- 결과 링크(코드)로 찾기
select r.id, r.user_id, r.created_at,
       r.user_id is null and r.created_at < now() - interval '90 days' as pii_purged_by_policy,
       r.respondent_name is not null as has_name,
       r.phone is not null as has_phone,
       r.email is not null as has_email,
       (select count(*) from diagnosis_leads l where l.result_id = r.id) as lead_count
  from diagnosis_results r
 where r.access_token = $1;          -- $1 = <결과 링크의 코드>

-- 회원의 결과 찾기
select r.id, r.created_at, (select count(*) from diagnosis_leads l where l.result_id = r.id) as lead_count
  from diagnosis_results r
 where r.user_id = $1                -- $1 = <회원 profiles.id>
 order by r.created_at desc;

-- 문의 확인
select l.id, l.result_id, l.user_id, l.status, l.created_at,
       l.message is not null as has_message, l.admin_note is not null as has_note
  from diagnosis_leads l
 where l.id = $1;                    -- $1 = <문의 id>
```

- 결과 링크 코드도 값이에요. 코드는 대화나 기록에 쓰지 않고, 조회할 때 입력 파일처럼 사람이 직접 넣어요. 대장에는 찾은 행의 `id`만 적어요.
- 이 조회도 같은 방식으로 트랜잭션 안에서 아래 형식의 접속 기록을 남겨요. `action='조회'`, `detail='table=diagnosis_results;id=<행 id>;fields=존재확인'`.
- 회원 결과의 연락처가 실제로 무엇인지 확인해야 하면 화면(`/admin/selfcheck/<id>`)에서 봐요. 그러면 화면이 자동으로 기록해요.

#### B. 정정 스크립트 템플릿

```js
// <접수번호>-correct.mjs : 정정 1건. 이 파일에 값(이름·연락처)을 쓰지 않아요. 실행 후 지워요.
import fs from 'node:fs';
import pg from 'pg';

const CASE = '<접수번호>';                     // 예: DC-20261127-01
const TABLE = '<diagnosis_results|diagnosis_leads>';
const ROW_ID = '<대상 행 id>';
const EXPECTED_USER_ID = null;                 // 회원 연결이면 '<회원 profiles.id>', 비회원이면 null
const ADMIN_ID = '<처리 관리자 profiles.id>';   // 요청을 받아 결정한 관리자. 실행자가 아니어도 이 값
const FIELDS = ['<항목>'];                      // 결과: respondent_name|phone|email, 문의: name|contact|message|admin_note
const INPUT = `${process.env.HOME}/bara-edu-ops/${CASE}.json`;
const IP = (process.env.SSH_CLIENT ?? '').split(' ')[0] || null; // 운영자 접속지(EC2 Instance Connect의 출발 IP)

const ALLOWED = {
  diagnosis_results: ['respondent_name', 'phone', 'email'],
  diagnosis_leads: ['name', 'contact', 'message', 'admin_note'],
};
if (!ALLOWED[TABLE] || FIELDS.length === 0 || FIELDS.some((f) => !ALLOWED[TABLE].includes(f))) throw new Error('bad FIELDS');

const c = new pg.Client({ connectionString: process.env.DATABASE_URL });
await c.connect();
try {
  const input = JSON.parse(fs.readFileSync(INPUT, 'utf8'));
  const vals = FIELDS.map((f) => {
    if (!(f in input)) throw new Error(`missing ${f}`);
    return input[f] === null ? null : String(input[f]).trim() || null;
  });

  await c.query('begin');
  await c.query('set local role bara_edu_service');

  const t = await c.query(`select user_id from ${TABLE} where id = $1 for update`, [ROW_ID]);
  if (t.rowCount !== 1) throw new Error('target not found');
  if ((t.rows[0].user_id ?? null) !== EXPECTED_USER_ID) throw new Error('owner mismatch');

  const sets = FIELDS.map((f, i) => `${f} = $${i + 2}`).join(', ');
  const u = await c.query(`update ${TABLE} set ${sets} where id = $1`, [ROW_ID, ...vals]);
  if (u.rowCount !== 1) throw new Error('update count');

  // 정정 뒤에도 지켜야 할 조건(값은 보지 않음)
  if (TABLE === 'diagnosis_results') {
    const v = await c.query(
      'select respondent_name is not null as n, (phone is not null or email is not null) as ct from diagnosis_results where id = $1',
      [ROW_ID],
    );
    if (!v.rows[0].n) throw new Error('name must not be null: use delete');   // 4장 마지막 줄, 8장 R2
    if (!v.rows[0].ct) throw new Error('need phone or email: use delete');
  } else {
    const v = await c.query('select name is not null and contact is not null as ok from diagnosis_leads where id = $1', [ROW_ID]);
    if (!v.rows[0].ok) throw new Error('name/contact must not be null: use delete');
  }

  await c.query(
    'insert into admin_access_logs (admin_id, target_user_id, action, detail, ip_address) values ($1, $2, $3, $4, $5)',
    [ADMIN_ID, EXPECTED_USER_ID, '정정요구처리', `table=${TABLE};id=${ROW_ID};fields=${FIELDS.join(',')}`, IP],
  );
  await c.query('commit');
  console.log('COMMIT', CASE, TABLE, ROW_ID, FIELDS.join(','));
} catch (e) {
  await c.query('rollback').catch(() => {});
  console.error('ROLLBACK', CASE, e.code ?? '', e.message);
  process.exitCode = 1;
} finally {
  await c.end();
  fs.rmSync(INPUT, { force: true });
}
```

#### C. 삭제 스크립트 템플릿

```js
// <접수번호>-delete.mjs : 삭제 1건. 값이 필요 없어요. 실행 후 지워요.
import pg from 'pg';

const CASE = '<접수번호>';
const TABLE = '<diagnosis_results|diagnosis_leads>';
const ROW_ID = '<대상 행 id>';
const EXPECTED_USER_ID = null;                 // 회원 연결이면 '<회원 profiles.id>'
const ADMIN_ID = '<처리 관리자 profiles.id>';
const EXPECTED_LEADS = 0;                      // 결과 삭제일 때 A 조회에서 본 lead_count. 문의도 지우기로 했으면 따로 C를 한 번 더 실행
const IP = (process.env.SSH_CLIENT ?? '').split(' ')[0] || null;

if (!['diagnosis_results', 'diagnosis_leads'].includes(TABLE)) throw new Error('bad TABLE');

const c = new pg.Client({ connectionString: process.env.DATABASE_URL });
await c.connect();
try {
  await c.query('begin');
  await c.query('set local role bara_edu_service');

  const t = await c.query(`select user_id from ${TABLE} where id = $1 for update`, [ROW_ID]);
  if (t.rowCount !== 1) throw new Error('target not found');
  if ((t.rows[0].user_id ?? null) !== EXPECTED_USER_ID) throw new Error('owner mismatch');
  if (TABLE === 'diagnosis_results') {
    const l = await c.query('select count(*)::int as n from diagnosis_leads where result_id = $1', [ROW_ID]);
    if (l.rows[0].n !== EXPECTED_LEADS) throw new Error('lead count changed');
  }

  await c.query(
    'insert into admin_access_logs (admin_id, target_user_id, action, detail, ip_address) values ($1, $2, $3, $4, $5)',
    [ADMIN_ID, EXPECTED_USER_ID, '삭제요구처리', `table=${TABLE};id=${ROW_ID};fields=row`, IP],
  );
  const d = await c.query(`delete from ${TABLE} where id = $1`, [ROW_ID]);  // 결과 삭제 시 diagnosis_answers는 함께 삭제, 문의의 result_id는 null
  if (d.rowCount !== 1) throw new Error('delete count');
  await c.query('commit');
  console.log('COMMIT', CASE, TABLE, ROW_ID, 'row');
} catch (e) {
  await c.query('rollback').catch(() => {});
  console.error('ROLLBACK', CASE, e.code ?? '', e.message);
  process.exitCode = 1;
} finally {
  await c.end();
}
```

- 회원 결과를 지울 때 `target_user_id`가 `profiles.id`를 참조하므로 회원 id를 그대로 넣을 수 있어요. 탈퇴한 회원도 `profiles` 행은 남아 있어서 넣을 수 있어요.
- 같은 사람의 결과가 여러 건이면 건마다 스크립트를 한 번씩 실행하고, 접속 기록도 건마다 한 줄씩 남겨요.

#### D. 접속 기록(`admin_access_logs`) 형식

| 컬럼 | 값 | 규칙 |
|---|---|---|
| `admin_id` | 처리 관리자의 `profiles.id` | 요청을 받아 처리를 결정한 관리자 계정이에요. DB를 실제로 만진 사람은 운영자 접근 기록(F)에 따로 남겨요 |
| `target_user_id` | 회원 연결 결과·문의: 그 회원 id. 비회원: **null** | 비회원은 `detail`의 행 id로 찾아요 |
| `action` | 정정: **`정정요구처리`**, 삭제: **`삭제요구처리`**, 사전 조회: `조회` | 화면 기능의 `정보수정`·`수정`과 다른 값이라 이 절차의 처리만 따로 걸러낼 수 있어요 |
| `detail` | `table=<테이블>;id=<행 id>;fields=<컬럼,컬럼>` (삭제는 `fields=row`, 사전 조회는 `fields=존재확인`) | **대상 id와 항목만.** 이전 값·새 값·사유 원문·접수번호·요청자 정보를 넣지 않아요. 기존 `정보수정`과 같은 `키=값;` 모양이에요 |
| `ip_address` | WAS 세션의 `SSH_CLIENT` 첫 값(운영자 접속지) | 비어 있으면 null로 두고 운영자 접근 기록에 접속지를 적어요 |
| `created_at` | 기본값(`now()`) | 넣지 않아요 |

접수번호·본인 확인 방법·확인자는 접속 기록이 아니라 처리 대장(부록 A)에 남겨요. 대장의 `대상 id`와 접속 기록의 `detail`로 둘을 맞춰 봐요.

#### E. 동료 확인

DB를 직접 고치면 화면의 검증이 하나도 없어서 두 사람이 봐요.

| 언제 | 확인자(실행자가 아닌 관리자)가 볼 것 | 남길 곳 |
|---|---|---|
| 실행 전 | ① 본인 확인을 마쳤는지(대장의 방법 칸) ② 4장 결정이 맞는지 ③ 스크립트 상수 `TABLE`, `ROW_ID`, `EXPECTED_USER_ID`, `FIELDS`, `ADMIN_ID`, `EXPECTED_LEADS` ④ 값이 스크립트 파일에 없는지 | 대장 "확인자" 칸 |
| 실행 후 | ① 출력이 `COMMIT`인지 ② 아래 확인 쿼리 결과 ③ 정정이면 상세 화면에서 새 값이 요청대로 들어갔는지(이 열람은 화면이 기록해요) | 대장 "실행 후 확인" 칸 |

```sql
-- 실행 후 확인(값 없이)
select count(*) from diagnosis_results where id = $1;   -- 삭제: 0
select count(*) from diagnosis_answers where result_id = $1;  -- 결과 삭제: 0
select action, detail, target_user_id is null as non_member, created_at
  from admin_access_logs
 where action in ('정정요구처리', '삭제요구처리') and detail like 'table=%;id=' || $1 || ';%';  -- 1건
```

**관리자가 대표 한 명뿐일 때(대표 결정 D1, 2026-11-26): 대표 혼자 처리하고 기록해요.** 동료 확인 대신 실행 전·후 표의 항목을 대표가 직접 하나씩 확인하고, 대장 "확인자" 칸에 `단독 처리(대표)`라고 적어요. 실수를 잡아 줄 사람이 없으므로 삭제는 실행 전에 확인 쿼리(`select count(*) … where id = $1` = 1, 소유자 일치)를 꼭 먼저 돌리고, 행 수가 예상과 다르면 롤백해요. 관리자가 늘면 위 표대로 다른 관리자가 확인해요.

- 실행이 끝나면 WAS의 스크립트 파일과 입력 파일을 지우고, 지운 사실을 같은 줄에 적어요.

1. 접수, 대장에 접수번호 부여 (2장)
2. 본인 확인 (3장). 실패하면 6.3절 거절 통지로 끝내요
3. 처리 방법 결정 (4장). 요청자에게 결과(예: 지우면 되돌릴 수 없어요)를 알리고 동의를 받아요
4. 대상 찾기 (5.1절, 5.2절 A)
5. 스크립트 준비, 동료 확인(실행 전) (5.2절 E)
6. 정정이면 처리 관리자가 입력 파일 작성 → 실행 (5.2절 B·C)
7. 동료 확인(실행 후), 운영자 접근 기록 추가 (5.2절 E·F)
8. 결과 통지 (6장), 대장 마감 (7장)

### 5.4 잘못 처리했을 때

- 정정 값이 틀렸으면 요청자에게 다시 확인하고 B를 한 번 더 실행해요(접속 기록 1건 추가). 이전 값은 어디에도 남기지 않으므로 되돌리기가 아니라 다시 고치기예요(정의서 Q3과 같은 원칙).
- 삭제는 되돌릴 수 없어요. 그래서 3장에서 삭제는 더 강하게 확인하고, 실행 전 동료 확인을 빼지 않아요.
- 엉뚱한 행을 고쳤거나 지웠으면 바로 대표(개인정보 보호책임자)에게 알려요. 유출이나 무단 변경에 해당하는지는 대표가 판단해요.

- 전화 메모: 종이에 쓰지 않는 것이 원칙이에요. 썼다면 처리를 마친 날 파쇄해요.

### 7.4 점검

매달 첫 영업일에 대표 또는 대표가 정한 관리자가 아래를 확인해요. 고시는 점검 주기를 내부관리계획으로 정하게 하고 있어요(2차 자료 기준, 원문 확인 필요). 건수가 적어서 매달 해도 부담이 작아요.

```sql
-- 지난달 이 절차의 처리 기록(값 없음)
select created_at, admin_id, target_user_id is null as non_member, action, detail
  from admin_access_logs
 where action in ('정정요구처리', '삭제요구처리')
   and created_at >= date_trunc('month', now()) - interval '1 month'
   and created_at <  date_trunc('month', now())
 order by created_at;
```

- 대장의 처리 건과 접속 기록이 1:1로 맞는지 확인해요. 대장에 없는 접속 기록이 있으면 무단 변경으로 보고 대표에게 알려요.
- 기한을 넘긴 건이 있는지 확인해요.
- 같은 요청이 석 달 연속으로 들어오면 관리자 화면에 정정·삭제 기능을 만드는 것을 product-manager에게 제안해요(정의서 Q6 "요구가 반복되면 그때 화면화").
- 이 조회도 DB 접근이므로 운영자 접근 기록에 `조회`로 한 줄 남겨요.

| R3 | 정정 값이 운영 작업 중에 대화 기록·명령줄·셸 이력에 남을 수 있어요 | 최소수집, 안전성 확보 | 주요 | 사람이 만드는 0600 입력 파일, 실행 후 삭제(5.2절 값 다루기 규칙). 지키지 못했으면 그 대화·파일을 지우고 대장에 남겨요 |
| R4 | 강사과정 문의의 상태 전환·메모 수정은 접속 기록이 없고, 메모 칸에 이름·연락처를 적지 못하게 막는 규칙도 없어요 | 처리방침 제8조 제5항("조회·처리할 때마다") | 권고 · **구현됨(2026-11-26)** | **코드 수정 권고**: `markLeadContacted`/`closeLead`/`updateLeadNote`에 접속 기록 추가, 메모에 정보 수정 기능과 같은 숫자 규칙 적용. 그 전까지는 정정 요청 때 `admin_note`도 함께 확인해요 메모는 관리자 메모와 같은 숫자·이메일 규칙(`memoHasPii`)을 쓰고 길이 제한은 두지 않아요(줄바꿈 허용). 배포 전에는 위 "그 전까지" 조치를 계속해요. |
| R5 | 진단 결과 상세 화면은 접속 기록 insert가 실패해도 원문을 보여 줘요(목록의 "개인정보 보기"는 막아요) | 처리방침 제8조 제5항 | 권고 · **구현됨(2026-11-26)** | 회원 상세와 같은 "가용성 우선" 선택이에요. 이번 절차에서는 상세 화면 열람 후 접속 기록이 남았는지 실행 후 확인에서 봐요 조회와 기록을 API 한 트랜잭션으로 묶어서 기록이 실패하면 원문 없이 안내만 나가요. 회원 상세(주소·사진 등)는 그대로 가용성 우선이에요. |
| R6 | 비회원 본인 확인 수단인 결과 링크는 공유될 수 있어요. 링크를 받은 사람이 삭제를 요청할 수 있어요 | 시행령 제46조 | 권고 | 링크 + 진단 당시 이름 일치를 함께 봐요. 처리 결과를 저장된 연락처로도 알려서 진짜 주인이 알 수 있게 해요(연락처가 남아 있을 때) |
| R7 | 처리방침 제8조 제5항은 접속 기록을 "최대 1년" 보관한다고 적었고, 코드는 1년이 되면 지워요. 2차 자료로 본 현행 고시는 "1년 이상"이고, 일부 조건(민감정보 처리 등)에서는 2년 이상이에요 | 안전성 확보조치 기준 제8조 | 주요(법 확인 필요) | 문구를 "1년 이상"으로 바꾸고 보관 기간을 1년보다 조금 길게(예: 1년 1개월) 잡는 것을 검토해요. 도형심리 결과가 민감정보인지에 따라 2년이 될 수 있어요(L3). **ceo-advisor 에스컬레이션 대상** |
| R8 | 접수·통지에 쓰는 info@ylia.io 메일 서비스가 처리방침 제5조 위탁 표에 없어요. 요청 메일에는 이름·연락처가 들어 있어요 | 법 제26조(위탁 공개) | 권고 | 메일 서비스 제공자를 확인하고, 위탁 표에 넣어야 하는지 L6과 함께 검토해요 |
