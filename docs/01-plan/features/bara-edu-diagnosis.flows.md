## 0. 원칙

- 정상 케이스만 적지 않는다 — 모든 플로우에 실패/예외 케이스를 붙인다.
- 애매한 정책은 임의로 정하지 않고 9절에 열린 질문(권장안 포함)으로 남긴다. 단, 화면 동작처럼 "developer가 구현 가능한 수준"이 필요한 세부사항은 service-planner가 합리적 기본값을 정해 명시하고, 그 근거를 함께 적는다(정책 vs 구현 디테일을 구분).
- 이미 구현된 화면(로그인/회원가입/마이페이지/관리자 신청·과제 관리)의 기존 상태·컴포넌트 패턴과 어긋나지 않는지 항상 대조한다. 이 문서 곳곳의 "기존 패턴 재사용" 각주가 그 대조 결과다.

## 0-1. 구현 전 공유 데이터 (원본 요구사항서 5~7절 근거)

스테퍼·결과 화면을 설계하는 데 반드시 필요한 원본 데이터를 여기 한 번에 정리한다(이후 각 절에서 재인용).

**영역 코드 ↔ 이름 ↔ DB 컬럼 (원본 §6~7, PM 문서 7.2절과 컬럼 순서 일치 확인됨)**

| 코드 | 영역명 | `diagnosis_results` 컬럼 | 문항 코드 |
|---|---|---|---|
| A | 기본이론 이해 | `score_theory` | A1~A5 |
| B | 도형 판독 능력 | `score_reading` | B1~B5 |
| C | 분석 능력 | `score_analysis` | C1~C5 |
| D | 상담·활용 능력 | `score_counseling` | D1~D5 |
| E | 사례 분석·기록 능력 | `score_case_record` | E1~E5 |
| F | 교육·지도 능력 | `score_teaching` | F1~F5 |

- 스테퍼 페이지 순서(2~7페이지)는 A→B→C→D→E→F 고정. PM 문서 Q4의 "영역 정의 순서(기본이론→…→교육지도)" 동점 처리 규칙과 동일한 순서라 하나의 순서 상수만 config에 두면 스테퍼/동점 처리 양쪽에 재사용 가능하다.
- 응답 척도는 0~4 **5단계**이며, 화면에는 숫자보다 **문구를 먼저** 노출한다(원본 §5).

| 점수 | 문구 |
|---|---|
| 0 | 처음 접한다 / 거의 알지 못한다 |
| 1 | 들어본 적 있다 |
| 2 | 설명할 수 있다 |
| 3 | 실제로 적용할 수 있다 |
| 4 | 다른 사람을 지도할 수 있다 |

- 라디오 그룹 각 옵션 레이블은 "문구"를 메인으로, 숫자는 보조(예: 작은 글씨 배지)로만 표기. 라디오는 `label` + `input` 명시적 연결(F-DIAG-18 접근성) 필수.

## 1. USER 플로우

### 1.1 진입 동선

```
홈 히어로 하단 진단 배너[나는 어떤 과정부터 시작하면 좋을까요?] (F-DIAG-2, Must)
  또는 헤더 "역량진단" (Should, Q9)
  또는 강좌 상세(도형기질활용지도자 트리) 보조 링크 "내 수준이 맞는지 확인하기" (Should)
  → /selfcheck (랜딩)
     제목 + "약 5분 · 30문항" + 비임상/비자격판정 고지 + CTA[진단 시작하기]
     → /selfcheck/start
```

| 화면/구성요소 | 동작 | 예외처리 |
|---|---|---|
| `/selfcheck` 랜딩 | 로그인 여부와 무관하게 동일 화면(`(public)` 그룹, `AppHeader`/`Footer` 자동 적용 — 홈과 동일 패턴) | — |
| CTA[진단 시작하기] | `/selfcheck/start`로 이동. 쿼리 파라미터 없음(항상 같은 진입점) | — |

### 1.2 `/selfcheck/start` 진입 시 — 임시저장 복원 분기 (F-DIAG-5)

페이지 마운트 시 클라이언트가 가장 먼저 하는 일:

```
localStorage["bara_selfcheck_draft_v1"] 확인
  ├─ 없음 → 1페이지(기본정보) 빈 폼으로 시작
  ├─ 있음 + version(DIAGNOSIS_VERSION) 불일치 → 조용히 삭제 후 빈 폼으로 시작
  ├─ 있음 + (now − savedAt) > 24시간 → 조용히 삭제 후 빈 폼으로 시작
  └─ 있음 + 24시간 이내 + version 일치
       → 확인 다이얼로그(native <dialog>, ConfirmDialog와 동일 시각 패턴)
         "작성하던 진단이 있어요. 이어서 진행할까요?"
         [이어서 하기] → 저장된 currentPage·기본정보·answers를 그대로 복원해 렌더
         [새로 시작하기] → localStorage 삭제 + 1페이지 빈 폼
```

- **저장 데이터 구조**: `{ version, savedAt, currentPage, basicInfo: {name, phone, email, learningExperience, certificateLevel, consentPrivacy, consentMarketing}, answers: {A1: 2, A2: 3, ...} }`. `consentPrivacy`/`consentMarketing`도 함께 저장해 복원 시 체크 상태까지 재현한다(체크박스만 빠뜨려 "다음"이 다시 막히는 경험 방지).
- **저장 시점**: 기본정보 각 필드 blur 시, 문항 라디오 선택 시, 페이지 이동 시마다 즉시 write(디바운스 불필요 — 로컬 저장이라 비용이 작다).
- **만료 기준(구현 디테일 결정, Q14 참고)**: "마지막 저장 시각 + 24시간"(rolling)으로 정의한다. 최초 저장 시각 기준으로 고정하면 오전에 5분 쓰다 멈춘 사용자가 그날 저녁에 이어하려 해도 이미 만료될 수 있어(활동은 계속 있었는데) UX상 불리하다. PM 문서 F-DIAG-5 문구("24시간 경과 시 삭제")는 기준 시점을 특정하지 않아 서비스 기획 수준에서 rolling으로 확정한다 — 정책적으로 민감하지 않은 구현 디테일이라 별도 승인 없이 진행하되, 이견 있으면 PO에게 이의 제기 가능.
- **새로고침(F5) / 브라우저 뒤로가기와의 관계**:
  - F5 새로고침 → React 상태는 초기화되지만 localStorage는 그대로 남아있어 위 "복원 분기"가 그대로 다시 실행된다. 즉 새로고침도 "나중에 재방문"과 동일한 흐름(확인 다이얼로그)을 탄다 — 새로고침 전용 특별 처리는 만들지 않는다(구현 단순화).
  - 스테퍼 내부의 "이전/다음"은 **브라우저 히스토리에 항목을 쌓지 않는다**(페이지 전환이 아니라 같은 라우트 안의 클라이언트 상태 변경). 따라서 사용자가 3페이지에 있는 상태에서 **브라우저 뒤로가기 버튼**을 누르면 스테퍼가 2페이지로 가는 게 아니라 `/selfcheck/start` 라우트 자체를 벗어나(예: `/selfcheck` 랜딩 또는 그 이전 방문 이력으로) 이동한다. 이때 응답은 localStorage에 남아있으므로, 사용자가 다시 [진단 시작하기]를 누르면 위 복원 다이얼로그가 뜨고 3페이지로 정확히 복귀한다 — 데이터 유실은 없지만 "뒤로가기 한 번으로 이전 문항 페이지로 못 돌아간다"는 점은 UX적으로 사용자에게 다소 낯설 수 있어 **엣지케이스 표에 별도 표기**(4절).

### 1.3 1페이지 — 기본정보 입력 (F-DIAG-3)

| 항목 | 필수여부 | 검증 규칙 | 실패 시 오류 문구 |
|---|---|---|---|
| 이름 | 필수 | 2자 이상 (회원가입 폼과 동일 기준) | "이름을 2자 이상 입력해주세요" |
| 휴대전화 | 필수 (Q1 CEO 확정) | 숫자만, 10~11자리, `010`류 형식 | "휴대전화 번호를 정확히 입력해주세요 (예: 01012345678)" |
| 이메일 | 필수 (Q1 CEO 확정) | 이메일 정규식 (auth.ts `EMAIL_RE`와 동일 패턴 재사용) | "이메일 형식이 올바르지 않아요" |
| 학습경험 (4지선다) | 필수 | 처음/과거수강/자격보유/현재활용 중 1개 라디오 선택 | "지금까지의 학습 경험을 선택해주세요" |
| 보유 자격 수준 | 선택 | — | — |
| 개인정보 수집·이용 동의 | 필수 체크 | `/legal/privacy` 링크 새 탭, 체크박스 | "개인정보 수집·이용에 동의해야 진단을 시작할 수 있어요" |
| ~~마케팅 수신 동의~~ | ~~선택 체크~~ | — | **폐기(2026-09-14)** — Phase 1은 실제 발송 기능이 없어 항목 자체를 제거 |

- **로그인 상태 프리필**: 로그인한 사용자가 `/selfcheck/start`에 오면 `profiles`의 name/phone/email로 세 필드를 프리필하되 **수정 가능**(진단은 다른 사람을 대신 진행할 수도 있으므로 읽기 전용으로 잠그지 않는다).
- **[다음] 클릭 시 검증 실패**: 첫 번째로 실패한 필드로 `scrollIntoView` + `focus()`, 해당 필드 하단에 위 표의 오류 문구를 인라인으로 노출(빨간 테두리). 여러 필드가 동시에 비어있어도 **한 번에 하나씩** 안내한다(기존 회원가입 폼이 필드별 검증이 아니라 `AuthFormState.error` 단일 문자열이므로, 진단 폼은 필드별 인라인 검증을 새로 도입하는 셈 — 아래 "구현 방식" 참고).
- **[다음] 클릭 성공** → 페이지 2(A영역, 기본이론)로 이동, `currentPage` localStorage 갱신.
- **[이전] 버튼**: 1페이지에는 표시하지 않음(뒤에 갈 곳이 없음).

**구현 방식 메모(개발자 참고, 정책 아님)**: 이 폼은 서버 왕복 없이 클라이언트에서 다음 페이지로 넘어가는 판단을 하므로(제출은 7페이지 완료 후 1번), `'use client'` 스테퍼 컨테이너가 각 페이지의 검증까지 담당한다. 최종 제출(1.5절)만 Server Action `submit_diagnosis()`를 호출한다 — `<form action={serverAction}>` 단일 제출 패턴이 아니라, `FormDialog`류처럼 클라이언트 상태를 오래 들고 있다가 마지막에 한 번 서버로 보내는 예외 패턴(AGENTS.md/CLAUDE.md가 언급한 "클라이언트 상태가 꼭 필요한 화면"에 해당).

### 1.4 2~7페이지 — 30문항 응답 (F-DIAG-4)

```
[상단 고정 영역]
  진행률 바: (지금까지 응답 완료한 문항 수 / 30) × 100%
  텍스트: "n/30문항 응답" + 현재 영역명 배지(예: "2/7 · 도형 판독 능력")
  (6개 영역 도트 인디케이터: 완료 영역은 채움, 현재 영역은 강조, 이후 영역은 빈 원 — 선택 사항, Should)

[본문]
  현재 영역 5문항을 세로로 나열
  각 문항: 문항 텍스트 + 5지 라디오(문구 우선, 숫자는 보조 배지)

[하단 고정 영역]
  [이전] (1페이지에서만 숨김) · [다음] (7페이지에서는 [제출하기]로 라벨 변경)
```

- **[다음] 클릭 시 검증**: 현재 페이지 5문항 중 미응답이 있으면 **다음 페이지로 진행 차단**.
  - 페이지 상단에 배너 노출: `"5문항 중 {n}문항에 아직 답하지 않았어요. 표시된 문항에 답해주세요."`
  - 미응답 문항 중 **첫 번째**로 `scrollIntoView({behavior:'smooth', block:'center'})` + 해당 문항 카드에 빨간 테두리 + 문항 하단에 `"이 문항에 답해주세요"` 인라인 문구.
  - 라디오를 선택하는 즉시 그 문항의 오류 표시는 사라진다(다른 문항까지 다시 검사할 필요 없음 — 개별 문항 단위로 오류 상태 관리).
- **[이전] 클릭**: 검증 없이 즉시 이전 페이지로 이동(이미 입력한 답은 유지). 답을 수정하고 다시 [다음]을 눌러도 이후 페이지 데이터에는 영향 없음.
- **응답 변경**: 라디오는 언제든 재선택 가능, 마지막 선택값이 저장됨.
- **7페이지의 [제출하기]**: 7페이지 5문항(F영역) 검증을 동일하게 통과해야 활성 동작. 클릭 즉시:
  1. 버튼 비활성 + 로딩 스피너 표시(중복 클릭/중복 제출 방지 — 기존 "제출 중 버튼 로딩" 패턴 승계, LMS flows.md 2.1)
  2. Server Action `submitDiagnosis(basicInfo, answers)` 호출 → 내부에서 `submit_diagnosis()` RPC 실행(F-DIAG-6)
  3. 성공 → localStorage draft 삭제 → `/selfcheck/result/[token]`로 이동(F-DIAG-7 판정 결과 포함해 즉시 리다이렉트)
  4. 실패(네트워크 오류·RPC 오류) → **localStorage draft는 삭제하지 않는다**(재시도 시 데이터 보존). 버튼 원상복구 + 인라인 오류: `"제출에 실패했어요. 잠시 후 다시 시도해주세요"` + [다시 시도] 버튼. 반복 실패 시 "문제가 계속되면 고객센터로 문의해주세요" 보조 문구 추가(3회 이상 실패 기준, Should).

### 1.5 서버 채점 · 추천 판정 (F-DIAG-6, F-DIAG-7) — 화면 관점 요약

- 클라이언트는 점수·추천 tier를 계산하지 않고 30개 원응답만 전달한다(기존 시험 RPC 신뢰 원칙 승계, LMS flows.md 2.4b와 동일 원칙).
- **이미 로그인한 상태로 진단을 제출하면** RPC가 생성 시점에 바로 `user_id = auth.uid()`, `claimed_at = now()`를 채워서 저장한다 — 이 경우 결과 페이지는 리다이렉트 직후부터 곧바로 **State C(로그인 후 상세)**로 렌더된다. claim 절차(1.6.3) 자체가 발생하지 않는다. *(PM 문서 F-DIAG-9는 "비회원이 만든 결과는 user_id=null"이라고만 명시했는데, 이 문서는 그 반대 경우 — 이미 회원인 경우 — 를 명시적으로 정의해 공백을 메운다.)*
- 비로그인 제출은 `user_id = null`로 생성되고, 응답 즉시 이동하는 결과 페이지는 **State A**로 시작한다.

### 1.6 결과 화면 — 3상태 (F-DIAG-8, F-DIAG-9)

라우트는 단일하다: `/selfcheck/result/[token]`. 렌더링되는 상태는 **① 로그인 여부, ② 그 결과의 `user_id`가 누구인지**의 조합으로 서버 컴포넌트가 결정한다. 클라이언트가 상태를 판단하지 않는다(게이팅 우회 방지 — qa-reviewer가 검증할 지점).

```
GET /selfcheck/result/[token]
  ├─ token에 해당하는 결과 없음 → "결과를 찾을 수 없음" 화면 (4절 엣지케이스)
  └─ 결과 있음
       ├─ 비로그인 → [State A] 요약 공개
       ├─ 로그인 + 결과.user_id == 현재 유저 → [State C] 상세 열람 (이미 귀속됨, 재귀속 없음)
       ├─ 로그인 + 결과.user_id == null → 아래 "claim 판단" 실행 → 성공 시 [State C], 거부 시 [State A]+안내
       └─ 로그인 + 결과.user_id == 다른 유저 → [State A-거부] "이미 다른 계정에 연결된 결과" 안내 (상세 절대 미노출)
```

#### 1.6.1 State A — 비로그인 요약 (F-DIAG-8)

**보이는 것**
- 추천 라벨(예: "기초부터 체계적으로 정리하는 단계")
- 전체 점수 (100점 만점, 숫자 하나)
- 추천 과정명 + 1~2문장 짧은 안내(점수 인용 없는 일반 문구 — tier 공통 카피, config)
- 비임상/비자격판정 고지 문구(모든 상태 공통, 상시 노출)
- 추천 강좌 CTA(F-DIAG-14, 아래 1.6.4)
- 잠금 안내 박스: `"영역별 점수, Radar 차트, 강점·보완 해석, PDF 저장은 로그인 후 확인할 수 있어요"` + [로그인] [회원가입] 버튼 2개
- (tier === `instructor_candidate`인 경우만) 강사과정 관심 문의 폼(F-DIAG-15, 1.7절) — **로그인 여부와 무관하게 이 시점부터 노출**(아래 "설계 결정" 참고)

**안 보이는 것** (요청이 와도 서버가 응답에 포함시키지 않음 — F-DIAG-8 "클라이언트 숨김 금지" 원칙)
- 6영역 개별 점수, Radar SVG, 강점/보완 영역 텍스트, 점수를 인용한 상세 추천 이유, PDF 저장 버튼
- **이름(respondent_name)** — 3.1절 토큰 설계 근거에 이미 "이름은 미노출"이라 명시되어 있음. 이 문서는 여기서 한 걸음 더 나아가 **요약을 보여주는 서버 조회(`get_diagnosis_summary(token)`) 자체가 이름·연락처를 리턴하지 않아야 한다**를 명시한다 — 단순히 프론트에서 안 보여주는 게 아니라 서버 응답에 애초에 없어야 한다(백엔드 RPC 계약에 반영 필요).

**설계 결정 — 리드 폼을 요약 단계(비로그인)부터 노출하는 이유 (Q12 관련)**: PM 문서 F-DIAG-15는 노출 시점(로그인 여부)을 specify하지 않았다. `instructor_candidate`는 최상위 tier로 전환 의지가 가장 높은 순간인데, 여기서 "로그인해야 문의할 수 있다"는 장벽을 추가로 세우면 가장 뜨거운 리드를 잃는다. 따라서 **요약 단계부터 노출**하는 것을 권장안으로 확정해 반영한다(9절 Q12로 PO 확인 요청은 남기되, 기본값은 이렇게 설계). 단, 아래 프리필 규칙으로 개인정보 노출 문제를 회피한다.

**리드 폼 프리필 규칙(개인정보 최소 노출과 UX 절충)**:
- 방금 이 브라우저에서 스테퍼를 제출해 이 결과 페이지로 **직접** 넘어온 경우에만, 제출 직후 클라이언트가 이미 메모리에 들고 있던 이름·연락처를 세션 단위(`sessionStorage`, 새 탭/재방문 시 사라짐)로 폼에 프리필한다.
- 그 외 모든 경우(링크를 나중에 다시 열었거나, 다른 사람이 공유받은 링크를 열었거나) — 폼은 **빈 값**으로 시작한다. 서버가 토큰 조회 응답에 이름·연락처를 포함시키지 않기 때문에 애초에 프리필할 데이터가 없다(의도된 설계 — 타인에게 이름·연락처가 새어나가지 않게 하는 방어가 자연스럽게 프리필 로직에도 적용됨).

> **미구현(2026-09-14 qa-reviewer 지적, 배포 차단 사유는 아님)**: 위 sessionStorage 기반 프리필과 아래 1.7절의 "동일 세션 중복 제출 시 완료 상태 노출"은 `LeadForm`에 `prefillContact` prop만 만들어두고 실제로 값을 채워 넣거나 sessionStorage 플래그를 읽는 로직은 아직 없다(현재는 `?leadSuccess=1` 쿼리파라미터가 붙어있는 그 요청에서만 완료 화면이 보이고, 페이지를 나갔다 재방문하면 사라진다). 서버가 tier·동의를 항상 재검증하므로 남용 위험은 없어 배포를 막을 사유는 아니지만, UX 완성도를 위해 후속 작업으로 남겨둔다.

#### 1.6.2 State B — 로그인/가입 유도 (전환 트리거)

State A 화면 안의 [로그인]/[회원가입] 버튼을 누르는 순간부터 State C에 도달하기까지의 실제 화면 이동이다. 두 경로가 동작 방식이 다르다(둘 다 이미 구현된 기존 화면을 그대로 재사용하되, "돌아올 곳"을 정확히 넘겨야 한다).

**경로 1 — [로그인]** (이미 회원인 사용자)

```
[로그인] 클릭 → /sign-in?redirect=/selfcheck/result/[token]
  (기존 safeRedirect() 오픈 리다이렉트 방지 로직 그대로 통과 — /selfcheck/... 는 내부 상대경로라 안전)
  → 로그인 성공 → app/actions/auth.ts login()의 redirect(redirectTo) → /selfcheck/result/[token] 복귀
  → 서버가 "로그인 + user_id==null" 조합을 감지 → claim 판단(1.6.3) 실행 → State C
```
기존 로그인 리다이렉트 패턴(`app/(public)/courses/[slug]/apply/page.tsx`와 동일한 `?redirect=` 관례)을 그대로 재사용하면 되므로 **추가 개발이 필요 없다**.

**경로 2 — [회원가입]** (신규 가입) — **여기가 기존 코드에 실제로 없는 기능 공백이다**

현재 구현(`app/actions/auth.ts` `signup()`, `components/auth/RecoveryRedirect.tsx`)을 확인한 결과:
- `signup()` 서버 액션은 `redirect` 파라미터를 아예 받지 않는다.
- 이메일 인증 링크를 눌렀을 때 세션을 만드는 `RecoveryRedirect`는 성공 시 **항상 `/my?welcome=1`로 고정 이동**한다.

즉 로그인 경로처럼 "돌아올 URL"을 왕복시킬 방법이 현재 없다 — 회원가입은 이메일 인증이라는 비동기 단계를 거치기 때문에(가입 화면 → 이메일 발송 → 사용자가 메일함에서 링크 클릭 → 그 링크가 `/my?welcome=1`로 착지) 일반적인 `?redirect=` 방식이 통하지 않는다.

**권장 처리 방식(Q10, 9절에서 재확인 요청)**: F-DIAG-5가 이미 "임시저장은 localStorage"라는 선례를 만들어 놓았으므로 같은 메커니즘을 한 번 더 쓴다.
```
[회원가입] 클릭
  → 클릭 핸들러가 localStorage["bara_selfcheck_pending_claim"] = { token, savedAt } 저장
  → /sign-up 이동(redirect 파라미터 없이 기존 화면 그대로)
  → (사용자가 메일함에서 인증 링크 클릭 — 최대 며칠 뒤일 수도 있음, 같은 브라우저/기기라는 전제)
  → RecoveryRedirect가 세션 생성 후 /my?welcome=1 도착 (기존 동작 변경 없음)
  → /my 페이지가 마운트 시 localStorage["bara_selfcheck_pending_claim"] 확인
       ├─ 없음 → 기존 동작 그대로(아무 일도 안 함)
       └─ 있음 + 7일 이내(이메일 인증까지 여유를 둠, 24시간보다 길게)
            → localStorage 삭제 → /selfcheck/result/[token]로 클라이언트 이동
            → 서버가 claim 판단 실행 → State C
```
- **전제 조건**: 인증 메일을 클릭하는 기기/브라우저가 가입을 시작한 기기/브라우저와 같아야 한다(다른 기기에서 메일을 확인하면 localStorage가 없어 그냥 `/my`에 남는다) — 완벽한 해법은 아니지만 추가 인프라(서버 세션에 pending claim 저장 등) 없이 기존 컨벤션만으로 대부분의 실사용 케이스(같은 폰/같은 브라우저로 이어서 진행)를 커버한다.
- **영향 범위**: `/my` 페이지에 이 확인 로직을 추가해야 하므로 이 부분은 기존 온보딩(`?welcome=1`) 동작에 조건부 분기 하나를 얹는 변경이다. 회원가입을 통해 들어온 일반 사용자(진단과 무관)에게는 해당 localStorage 키가 없으므로 아무 영향이 없다.

#### 1.6.3 State C — 로그인 후 상세 (F-DIAG-9, claim 로직)

**claim 판단 로직** (State B에서 돌아왔을 때, 또는 로그인 상태로 결과 페이지에 직접 진입했을 때 매번 실행):

```
결과.user_id == null 인가?
  ├─ No (이미 누군가에게 귀속됨)
  │    └─ 그 user_id == 현재 로그인 사용자? → Yes: 그대로 State C / No: "이미 다른 계정에 연결됨" 거부 (아래)
  └─ Yes (미귀속)
       └─ 이 브라우저가 "방금 이 결과를 직접 제출한 세션"인가?
            ├─ Yes → 확인 없이 즉시 claim 실행(user_id=현재유저, claimed_at=now) → State C
            └─ No  → claim 실행 전에 확인 다이얼로그 노출(Q11, 아래 "안전장치" 참고)
                     → [연결하기] → claim 실행 → State C
                     → [취소] → State A로 유지(로그인은 된 채로, 이 결과와는 연결하지 않음)
```

**구현 시 변경됨(2026-09-14, qa-reviewer + privacy-security-officer 지적)**: 이 절이 원래 제안한 "sessionStorage 플래그로 판단"은 실제 구현에서 **클라이언트가 URL에 붙인 `?claim=auto` 쿼리파라미터를 서버가 그대로 신뢰하는 방식**으로 잘못 구현됐다 — 공유받은 결과 링크를 아무나 열어 로그인 버튼만 눌러도 이 파라미터가 항상 붙어 확인 없이 귀속되는 치명적 결함이었다. 수정본은 sessionStorage보다 한 단계 더 안전한 **httpOnly 쿠키**를 쓴다: `submitDiagnosis()`가 제출 성공 직후 그 토큰 값을 담은 httpOnly 쿠키(`RECENT_SUBMIT_COOKIE`, 24시간, `/selfcheck` 경로)를 심고, 결과 페이지는 이 쿠키와 URL의 토큰이 일치할 때만 "방금 이 결과를 직접 제출한 세션"으로 판단한다. sessionStorage와 달리 클라이언트 JS가 값을 읽거나 위조할 수 없어(httpOnly) 더 강한 보장을 준다.

**claim 원자성(동시성)**: `admin-enrollments.ts`의 조건부 update 패턴을 그대로 승계한다 — `update(...).eq('id', resultId).eq('user_id', null).select()`. 두 요청이 동시에 들어와도(같은 사용자가 여러 탭을 열었거나, 극히 드물게 서로 다른 두 사용자가 거의 동시에 접근) 먼저 반영된 쪽만 성공하고 나중 쪽은 `data.length === 0`으로 실패를 감지해 재조회 후 최신 상태(이미 귀속됨)를 기준으로 다시 분기한다.

**안전장치를 두는 이유(Q11)**: PM 문서 F-DIAG-9는 "토큰 URL을 가진 사용자가 로그인/가입을 마치면 최초 1회 claim"이라고만 되어 있어, 문자 그대로 구현하면 **토큰을 가진 사람이 누구든(제3자 포함) 로그인만 하면 즉시 자기 계정에 연결**된다. 실제 시나리오: 진단을 받은 사람이 결과 링크를 배우자·동료에게 카톡으로 공유한 뒤 정작 본인은 로그인을 미루고 있는데, 링크를 받은 상대가 이미 로그인된 상태로 그 링크를 열면 — 문자 그대로 구현 시 상대방 계정으로 결과가 채여간다. "방금 이 브라우저에서 직접 제출했는지"로 자동/확인 여부를 가르면 이 사고를 막을 수 있다. 이 판단 로직은 이번 문서에서 **새로 설계**한 것이라 9절 Q11로 PO 확인을 요청한다.

**이미 다른 계정에 연결된 결과에 접근한 경우 — 거부 화면**
- 상세 데이터는 절대 반환/렌더하지 않는다.
- 화면: `"이 진단 결과는 이미 다른 계정에 연결되어 있어요"` + `"본인의 결과가 맞다면 고객센터로 문의해주세요"` (어느 계정에 연결됐는지는 노출하지 않음 — 이메일 열거 방지와 동일한 원칙, `auth.ts`의 "이메일 또는 비밀번호가 올바르지 않아요" 문구 설계와 같은 결)
- 요약(State A에 해당하는 공개 정보)까지 다시 보여줄지, 아예 이 거부 문구만 보여줄지는 **요약 표시가 게이팅 위반이 아니므로(요약은 원래 공개) 함께 보여줘도 무방** — 다만 로그인 상태에서 "로그인/가입 유도" 박스는 의미가 없으므로 그 자리를 위 거부 안내로 대체한다.

**State C에서 보이는 것** (State A 전체 + 아래 추가)
- 6영역 점수 표(수치 + 막대, 색상 비의존 — F-DIAG-10)
- Radar SVG(6축, 인라인 SVG polygon) + 스크린리더용 수치 표 병기(F-DIAG-11)
- 강점 1~2개 / 보완 1~2개 해석 문구(F-DIAG-12, 동점 처리는 PM 문서 Q4 확정 규칙 그대로 적용)
- 추천 이유 상세(점수 인용 포함, 예: "도형판독 48점") (F-DIAG-13)
- [PDF로 저장] 버튼 — 브라우저 인쇄 스타일시트 기반, 클릭 시 `window.print()`. 인쇄 미리보기에서는 헤더/네비/CTA/리드폼 숨김, 점수·차트·해석만 노출(F-DIAG-16)
- "마이페이지에서 다시 보기" 안내(F-DIAG-17 연결)
- 강사과정 리드 폼(tier 일치 시) — 이제는 서버가 소유자 검증을 마쳤으므로 `profiles`에서 이름/연락처를 안전하게 프리필 가능(1.7절)

### 1.7 강사과정 관심 문의 리드 폼 (F-DIAG-15)

**노출 조건**: `recommended_tier === 'instructor_candidate'`일 때만, State A·State C 양쪽 결과 화면에 동일 컴포넌트로 렌더(데이터 소스만 다름 — 1.6.1/1.6.3 참고).

**입력 항목**

| 필드 | 필수 | 검증 | 비고 |
|---|---|---|---|
| 이름 | 필수 | 2자 이상 | State A: sessionStorage 프리필 또는 빈값 / State C: `profiles.name` 프리필(수정 가능) |
| 연락처 | 필수 | 휴대전화 형식 또는 이메일 형식 중 하나만 맞으면 통과(느슨한 단일 필드 — `diagnosis_leads.contact`가 단일 text 컬럼인 스키마와 일치) | 위와 동일 프리필 규칙 |
| 한 줄 메모 | 선택 | 최대 100자 | placeholder: "궁금한 점이나 하고 싶은 말을 남겨주세요" |
| 연락 수신 동의 | 필수 체크 | — | `consent_contact` |

**제출 흐름**

```
[안내받기 신청] 클릭 → Server Action submitDiagnosisLead(resultToken, formData)
  (useActionState + 인라인 렌더 패턴 — components/auth/AuthForm.tsx와 동일한 구현 방식.
   FormDialog/ConfirmDialog는 모달 트리거용이라 이 화면처럼 결과 페이지에 상시 노출되는
   인라인 폼에는 맞지 않는다 — 페이지 내비게이션 없이 그 자리에서 성공/실패를 보여준다)
  → 서버: token → 내부 result_id 조회(클라이언트에는 내부 id를 절대 노출하지 않음, 3.1절 토큰 설계 원칙과 동일)
       → diagnosis_leads insert (result_id, user_id(로그인 시), topic='instructor_course', name, contact, message, consent_contact, status='new')
  → 성공 → 폼 자리를 성공 메시지로 교체: "문의가 접수됐어요. 강사과정 소식이 준비되면 안내드릴게요"
       → sessionStorage["bara_selfcheck_lead_submitted_{token}"] = 1 저장
          (같은 브라우저에서 이 결과 페이지를 다시 열면 폼 대신 "이미 문의를 남겼어요" 상태로 렌더 — 중복 제출 예방, 완전 차단은 아님)
  → 실패
```

| 실패 케이스 | 처리 |
|---|---|
| 이름 미입력 | "이름을 입력해주세요" + 필드 포커스 |
| 연락처 미입력/형식 오류 | "연락 가능한 휴대전화 번호나 이메일을 입력해주세요" + 필드 포커스 |
| 연락 수신 동의 미체크 | "연락 수신에 동의해야 접수할 수 있어요" + 체크박스 강조 |
| 서버/DB 오류 | "문의 접수에 실패했어요. 잠시 후 다시 시도해주세요" (입력값 유지, `useActionState`가 재렌더해도 uncontrolled input 값은 남아있음) |
| 남용(동일 연락처 단시간 반복 제출) | PM 문서 Q7(비회원 공개 쓰기 경로 남용 방지)과 동일 정책 적용 — 신규 규칙 아님, 참조만 |

- **자동 회신/자동 발송 없음**(W7 승계) — 성공 메시지 외에 이메일/문자 발송을 하지 않는다.
- 강좌 상세/신청 페이지로는 어떤 경우에도 연결하지 않는다(W4 승계).

## 2. ADMIN 플로우

### 2.1 진단 결과 목록·상세 (F-ADMDG-1, F-ADMDG-2) — 요약

기존 `/admin/enrollments` 목록·상세 패턴을 그대로 승계하므로 신규 상태 설계는 없다. 핵심만 명시:

- 목록 `/admin/selfcheck`: 최신순, 컬럼(일시/이름/**마스킹 연락처**/학습경험/전체점수/추천 tier/회원 귀속 여부), 필터(tier/기간/회원-비회원), 검색(이름/연락처, Q8). 연락처 마스킹은 기존 F-ADM-3 패턴(`lib/supabase/admin-queries.ts`의 마스킹 유틸) 재사용 — 신규 마스킹 규칙 만들지 않는다.
- 상세 `/admin/selfcheck/[id]`: 6영역 점수 + 강점/보완 + 응답 30건 원본(`diagnosis_answers`) 표. 회원 귀속 시 `/admin/members/[id]` 링크.
- **관리자 열람 로깅**: PM 문서가 F-ADMDG-2에 "검토 필요"로 남겨둔 `admin_access_logs` 적용 여부는 그대로 열린 채로 둔다(9절에서 F-ADMDG-3 리드 화면까지 범위를 넓혀 재확인 요청, Q15).

### 2.2 강사과정 리드 관리 (F-ADMDG-3) — 상태 전환 상세

**목록 `/admin/selfcheck/leads`**

| 컬럼 | 내용 |
|---|---|
| 접수일시 | `created_at` |
| 이름 | `name` |
| 연락처 | 마스킹 표시(F-ADM-3 패턴), 상세 확장 시 원문 |
| 메모 | `message` 1줄 요약(말줄임) |
| 연결된 진단 결과 | `result_id` 있으면 "진단결과 보기" 링크 → `/admin/selfcheck/[id]`, 없으면 "—" (Phase 1에서는 F-DIAG-15가 유일한 접수 경로라 항상 존재하지만, `topic` 컬럼이 향후 다른 문의 유형으로 확장될 것을 대비해 null 케이스도 화면에 정의해둔다) |
| 상태 | 배지: 신규(회색) / 연락함(파랑) / 종료(초록 또는 n-4 톤) |
| 담당자 | `handled_by` → 관리자 이름, 미처리 시 "—" |
| 처리일시 | `handled_at`, 미처리 시 "—" |

**필터**: 상태(전체/신규/연락함/종료), 기간. **검색**: 이름/연락처(Q8과 동일 기준 적용).

**상태 전환 플로우**

```
[신규] ──[연락함으로 표시]──▶ [연락함] ──[종료 처리]──▶ [종료]
   │                                                        ▲
   └────────────────[바로 종료]─────────────────────────────┘
```

| 액션 | 트리거 위치 | 컴포넌트 | 사유 입력 | 서버 처리 (동시성 패턴은 `admin-enrollments.ts`/`admin-assignments.ts`와 동일) |
|---|---|---|---|---|
| 연락함으로 표시 | 상태=`new`인 행 | `ConfirmDialog`(reasonField는 선택 — 통화 메모를 남기고 싶을 때만 입력, `required` 아님) | 선택 | `update(...).eq('id', leadId).eq('status','new').select()` → `status='contacted', handled_by=현재관리자, handled_at=now(), admin_note=입력값(있으면)` |
| 바로 종료 | 상태=`new`인 행 | `ConfirmDialog`(reasonField 필수 — 예: "중복 접수", "연락 불가") | **필수** | `.eq('status','new')` → `status='closed', admin_note=사유, handled_by, handled_at` |
| 종료 처리 | 상태=`contacted`인 행 | `ConfirmDialog`(reasonField 필수 — 예: "강사과정 안내 완료", "본인 의사로 보류") | **필수** | `.eq('status','contacted')` → `status='closed', admin_note=사유(기존 메모에 append), handled_at 갱신` |
| 메모만 수정 | 임의 상태 | `FormDialog`(textarea 1개) | — | `admin_note`만 update, 상태는 변경하지 않음 |

- 각 전환은 `.eq('id', leadId).eq('status', 이전상태)` 조건부 update + `data.length === 0`이면 "이미 처리됨" 토스트 — 여러 관리자가 동시에 같은 리드를 처리하는 충돌을 막는 기존 패턴 그대로.
- **재오픈(종료 → 신규/연락함) 액션은 Phase 1에 두지 않는다**(구현 디테일 결정, Q13 참고): 리드 워크플로는 신규→연락함→종료의 단방향으로 충분히 단순하고, `admin-enrollments.ts`에 있는 "승인 취소"류 반전 액션은 입금·수료라는 되돌리기 필요성이 명확한 도메인이라 만든 것이었다. 잘못 종료한 경우는 관리자가 `admin_note`에 정정 사유를 남기는 것으로 우선 대응하고, 재오픈 요구가 실제로 나오면 Phase 2에서 추가한다.
- 리드 상세는 별도 라우트를 만들지 않고 목록 행 확장(아코디언) 또는 우측 패널로 충분(기존 `/admin/enrollments` 목록+상세패널 패턴, LMS flows.md 4절 "Admin 신청·입금 관리" 참조) — 신규 상세 화면 불필요.

## 5. 열린 질문

### 5.1 PM 문서 승계 (재확인 불필요, 참조만)

Q1~Q3(연락처 필수/1급 강좌 존재/미귀속 보유기간)은 CEO가 이미 확정했고 이 문서 전체에 그대로 반영했다. Q4(동점 처리)·Q5(PDF)·Q6(GA4)·Q7(남용 방지)·Q8(관리자 검색)·Q9(헤더 노출)는 PM 문서 그대로 열려 있으며, 이 문서의 설계는 전부 그 열린 상태를 전제로 작성했다(예: Q7의 결론이 무엇이든 1.4/1.7절의 "제출 흐름" 골격은 바뀌지 않는다).
