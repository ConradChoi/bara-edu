# 비밀번호 찾기(재설정 메일 요청) 화면 정의서

- 작성일: 2026-11-26
- 작성: service-planner
- 근거: 대표 지시 2026-11-26 (회원 스스로 재설정 메일 요청, 본인 확인은 이메일만 하고 휴대폰 본인인증은 하지 않는다)
- 상태: 초안. 10장의 질문에 대표 답변이 오면 확정한다. 코드는 바꾸지 않았다.
- 문구: 이 문서의 문구는 초안이다. 최종 문구는 ux-writer가 정한다. 말투 기준은 `bara-edu-lms.signup-enumeration-copy.md`(쉬운 `~해요`체, 이모지·느낌표 없음, 사용자를 탓하지 않기)를 따른다.
- 검토 필요: 이메일 주소를 입력받고 메일을 보내므로 privacy-security-officer 점검 후 배포한다(8장). API는 이미 있어 계약 변경은 필수가 아니다(5장). 앱 쪽 호출 함수의 반환값만 넓혀야 한다.
- 관련 문서: `bara-edu-lms.signup-verify-password.md`(가입 마무리, 이하 "가입 마무리 문서"), `bara-edu-lms.signup-enumeration-copy.md`(이하 "열거 방지 문서")

미인증 계정이 재설정 링크로 확정되는 것은 코드와 테스트로 확인했다(`resetPassword`의 `coalesce(email_confirmed_at, now())`, `api/test/auth-signup.test.ts` 513행 테스트). 그 테스트 이름에 "앱 화면에는 이 요청 경로가 없다"고 적혀 있어, 이 화면이 생기면 이름을 고쳐야 한다.

## 1. 핵심 설계 (한눈에)

1. 새 화면 1개: `/forgot-password` (이름 제안, `(auth)` 그룹의 카드형. 로그인·가입·재설정과 같은 레이아웃). 입력 상태와 "보냄" 상태를 한 화면에서 바꾼다(가입 화면의 `pendingConfirmation` 방식과 같다).
2. 이메일만 묻는다. 가입 여부, 계정 상태, 관리자 여부와 관계없이 화면·문구·이동이 항상 같다.
3. 링크로 들어온 뒤 화면은 이미 있는 `/reset-password`를 그대로 쓴다. 다만 만료·오류 때 다시 요청할 길이 없어 연결을 추가한다(3장).
4. 이 화면은 "가입 방해" 대응 경로이기도 하다. 재설정 한도(`reset-*`)는 가입·재전송 한도(`resend-*`)와 따로 센다. 그래서 공격자가 재가입으로 메일 한도를 소진해도 피해자의 재설정 메일은 영향받지 않는다(가입 마무리 문서의 "위험 감수 기록"에 있는 한도 공유 문제를 이 경로는 비껴간다). 재설정 링크를 쓰면 인증도 함께 끝나고 공격자의 가입 시도는 모두 삭제된다.
5. 본인 확인은 "메일함을 열 수 있는 사람"이 전부다(대표 결정 2026-11-26). 이름·연락처·휴대폰 인증은 묻지 않는다.

### 1.2 시나리오 단계

정상(비밀번호를 잊은 가입 회원)
1. 로그인 화면에서 [비밀번호를 잊으셨나요?]를 누른다 → `/forgot-password`.
2. 가입한 이메일을 입력하고 [재설정 메일 받기]를 누른다.
3. 보냄 화면이 뜬다("메일함을 확인해 주세요").
4. 메일의 [비밀번호 재설정] 링크를 연다 → `/reset-password?token=`.
5. 새 비밀번호를 두 번 입력하고 [비밀번호 변경]을 누른다.
6. `/sign-in?reset=1`에서 새 비밀번호로 로그인한다. (모든 기기에서 로그아웃되어 있다.)

가입 방해를 당한 피해자(가입 마무리 문서의 공격 시나리오 이후)
1. 피해자가 여러 통의 가입 안내 메일을 받고 어느 링크도 비밀번호가 맞지 않아 열지 못한다(또는 5회 틀려 잠금).
2. 가입 마무리 화면의 "비밀번호가 기억나지 않아요" 영역이나 잠김 화면에서 [비밀번호 다시 정하기]를 누른다 → `/forgot-password`.
3. 자기 이메일을 입력하면 재설정 메일이 자기 메일함으로 온다. 공격자는 이 메일을 받을 수 없다.
4. 링크에서 새 비밀번호를 정하면 계정이 확정(인증 완료)되고 모든 가입 시도·가입 링크가 무효가 된다. 로그인한다.
5. 프로필의 이름·연락처는 "처음 가입 시도" 값이라 공격자가 넣은 값일 수 있다(4.3절, 질문 7).

## 2. 화면 정의: `/forgot-password`

- 경로: `app/(auth)/forgot-password/page.tsx` (제안). 서버 렌더 + 클라이언트 폼(`useActionState`, JS 없이도 `<form action>`으로 제출 가능. 가입 마무리 문서의 인앱 브라우저 대비와 같다).
- 접근: 로그인 여부와 무관하다. 로그인 상태로 열어도 막지 않는다(구현 때 `proxy.ts`의 로그인 상태 리다이렉트 목록을 확인해 이 경로가 `/my`로 튕기지 않게 한다). 로그인 상태에서는 화면 아래에 "로그인한 상태라면 마이페이지에서 바꿀 수 있어요" 한 줄과 `/my` 링크를 둔다(선택).
- 응답 헤더: 이메일을 URL에 담지 않으므로 필수는 아니지만 `Cache-Control: no-store`, `X-Robots-Tag: noindex`를 건다(검색 노출 불필요).
- 이메일을 URL(`?email=`)로 넘기지 않는다. 주소가 접근 로그·Referer·브라우저 기록에 남기 때문이다(질문 6). 로그인 화면에서 이미 쓴 이메일이 있어도 다시 입력하게 한다.

### 2.1 상태별 화면

| 상태 | 제목 | 보여 줄 것 | 버튼·링크 |
|---|---|---|---|
| 입력 (기본) | 비밀번호 찾기 | 안내 한 줄, 이메일 칸 | [재설정 메일 받기], [로그인 화면으로] |
| 제출 중 | (입력과 같음) | 버튼만 "보내는 중이에요"로 바뀌고 비활성, 칸은 읽기 전용이 아니라 그대로 둔다 | 중복 제출 방지 |
| 보냄 (200) | 메일함을 확인해 주세요 | 입력한 이메일, 안내 문구, 메일이 안 올 때 안내, 다시 받기 영역 | [메일 다시 받기](60초 뒤 활성), [다른 이메일로 다시 입력], [로그인 화면으로] |
| 형식 오류 | (입력 유지) | 칸 아래 "올바른 이메일 형식이 아니에요"(서버 호출 없음. 회원 여부와 무관하므로 열거 위험 없음) | — |
| 횟수 초과 (429) | (입력 유지) | 칸 위 알림 "요청이 많아요. 잠시 후 다시 시도해 주세요"(`MSG_RATE_LIMITED` 재사용). 입력값 유지 | 같은 버튼 다시 사용 가능 |
| 연결 불가 (503·네트워크) | (입력 유지) | "지금 연결이 원활하지 않아요. 잠시 후 다시 눌러 주세요"(`MSG_UNAVAILABLE` 재사용). 입력값 유지 | 같은 버튼, 전화 문의 |
| 기타 실패(400 origin 등 서버 설정 문제) | (입력 유지) | "메일을 보내지 못했어요. 잠시 후 다시 시도해 주세요. 계속 안 되면 전화로 문의해 주세요. `{siteConfig.phone}`" | 같은 버튼, 전화 문의 |
| 로딩(페이지 진입) | — | 서버 렌더라 스피너 없음 | — |

- "횟수 초과"는 **IP 제한(429)일 때만** 보인다. 이메일별 제한(60초 1회·1시간 4회)에 걸린 경우 API는 메일을 보내지 않고도 똑같이 200을 주므로 화면은 "보냄"과 같다. 이 차이를 화면에서 드러내면 이메일 열거가 된다(그 이메일에 최근 요청이 있었다는 사실과 계정 존재 여부는 별개이지만, 한도가 계정 여부와 상관없이 센다는 점을 지키려고 구분하지 않는다).
- 그 대신 보냄 화면에서 다시 받기 버튼을 60초간 비활성으로 두고, "1분 뒤에 다시 눌러 주세요"를 모두에게 같이 보여 준다(서버 `reset-60s`와 맞춤).

### 2.3 "보냄" 화면의 요소

| 요소 | 내용 | 동작 |
|---|---|---|
| 제목 | 메일함을 확인해 주세요 | 화면이 바뀌면 이 제목으로 포커스를 옮긴다(`tabIndex=-1`) |
| 본문 | `{email}`로 안내를 보냈어요. 가입한 이메일이 맞다면 몇 분 안에 비밀번호를 새로 정하는 링크가 도착해요. 링크는 1시간 동안 쓸 수 있어요. | 가입 여부를 단정하지 않는다(질문 1). 이메일은 `break-all`로 줄바꿈 |
| 메일이 안 올 때 | 몇 분이 지나도 없다면 스팸메일함을 확인해 주세요. / 입력한 이메일 주소가 맞는지 확인해 주세요. / 그래도 없으면 전화로 문의해 주세요. `{siteConfig.phone}` (`{siteConfig.supportHours}`) | 열거 방지 문서 2장 "메일이 안 올 때"와 같은 구성 |
| 다시 받기 | [메일 다시 받기] + 보조문 "여러 번 눌러도 메일이 빨리 오지 않아요. 1분 뒤에 다시 눌러 주세요" | 같은 이메일로 다시 제출. 보냄 직후 60초간 비활성(남은 초는 눈으로만 갱신하고 스크린리더에는 시작·종료 때만 알린다, 7장). 다시 제출하면 같은 화면을 유지하고 "다시 보냈어요" 문구를 한 줄 갱신하는 정도로 한다 |
| 다른 이메일 | [다른 이메일로 다시 입력] | 입력 화면으로 돌아가며 칸을 비운다 |
| 이동 | 로그인 화면으로 | `/sign-in` |
| 안내 | 본인이 요청하지 않았다면 따로 하실 일은 없어요. | 남이 내 주소로 요청한 경우 대비 |

## 3. 재설정 링크로 들어온 뒤의 흐름 (`/reset-password?token=`)

링크 도착 화면은 이미 구현돼 있다. 흐름은 그대로 이어 붙이고, 다시 요청할 길이 없는 곳만 보완한다.

| 상태 | 지금 | 정의(변경분만 표시) |
|---|---|---|
| 정상(토큰 있음) | 새 비밀번호·확인 두 칸, [비밀번호 변경] | 유지. 세 가지만 보완: (a) 두 칸에 [보기]/[숨기기] 추가(`PasswordField` 재사용. 가입 폼의 대표 결정 3과 같은 규칙), (b) 안내 한 줄 "변경하면 모든 기기에서 로그아웃돼요"(서버가 세션을 모두 지운다), (c) `autocomplete="new-password"` |
| 토큰 없음·형식 오류 | "링크가 올바르지 않아요. 재설정 이메일을 다시 요청해 주세요." + [로그인 화면으로] | 문구 유지, **[재설정 메일 다시 받기] → `/forgot-password` 링크 추가**(주 버튼), [로그인 화면으로]는 보조 |
| 만료·이미 사용·잘못된 토큰(제출 뒤 400 `invalid_token`) | 칸 위에 "비밀번호 변경에 실패했어요. 링크가 만료됐을 수 있어요. 다시 요청해 주세요."(요청할 링크 없음) | 문구 유지, **[재설정 메일 다시 받기] 링크 추가**. 입력한 비밀번호는 지우지 않는다(다시 요청해도 새 링크에서 다시 입력해야 하므로 의미는 적지만, 단순 오타 재시도가 가능하다) |
| 비밀번호 규칙 오류 | "비밀번호는 8자 이상이어야 해요" / "비밀번호가 일치하지 않아요" | 유지 |
| 429·연결 불가 | 지금은 일반 실패 문구로 묶임 | `reset-password`에는 IP 제한이 없어 429는 없다. 연결 불가(503)는 "지금 연결이 원활하지 않아요" 구분을 권장(`MSG_UNAVAILABLE`) |
| 성공 | `/sign-in?reset=1` 배너 "비밀번호가 변경됐어요. 새 비밀번호로 로그인해 주세요." | 한 줄 추가 "다른 기기에서는 다시 로그인해야 해요". 자동 로그인은 하지 않는다(메일 스캐너·공용 PC 위험) |
| 링크 미리보기·메일 스캐너가 링크를 연다 | GET은 토큰을 쓰지 않고 폼만 보여 준다(토큰은 POST에서 소모) | 유지 확인. 가입 마무리와 달리 읽기 전용 확인 API가 없어, 만료 링크는 비밀번호를 입력해 제출한 뒤에야 알 수 있다 → 질문 4 |
| 헤더 | `/reset-password`에 no-store·no-referrer·noindex가 없다 | `next.config.ts`에 `/reset-password`용 헤더 추가(가입 마무리의 `CONFIRM_PAGE_HEADERS` 재사용). URL의 토큰이 Referer·캐시로 새지 않게 한다. 폼 안에 외부 링크·외부 스크립트를 두지 않는다 |

링크를 쓴 뒤 로그인 화면에서 미인증 계정이었던 회원이 헷갈리지 않도록 별도 분기는 두지 않는다. 재설정으로 인증이 함께 끝났으므로 같은 `?reset=1` 배너로 충분하다.

## 4. 계정 유형별 동작

공통: 화면과 응답은 모든 유형에서 같다(2장). 아래는 메일이 실제로 가는지, 링크를 썼을 때 무슨 일이 생기는지다.

| 계정 유형 | 요청 시 메일 | 링크를 쓴 결과 | 비고 |
|---|---|---|---|
| 일반 회원(인증 완료) | 간다 | 새 비밀번호 설정, 모든 세션 삭제, 모든 토큰 무효 | 기본 경로 |
| 가입 없음(없는 이메일) | 안 간다 | — | 화면 같음. `reset-miss` 제한 기록만 남음 |
| 미인증 계정(가입 마무리 전, 비밀번호 칸 비어 있음) | 간다(`auth.users` 행이 있으면 보낸다) | 새 비밀번호를 정하고 **인증도 함께 완료**. 그 계정의 가입 시도(공격자 비밀번호 해시 포함)와 가입 링크는 모두 삭제·무효 | 가입 방해 복구 경로. 로그인까지는 `/sign-in`에서 새 비밀번호로 한다. 프로필의 이름·연락처는 첫 가입 시도 값이라 틀릴 수 있다(4.3절) |
| 비밀번호가 비어 있는 인증 완료 계정(옛 `verify-email` 롤백 사고 등) | 간다 | 비밀번호가 새로 설정돼 로그인 가능 | 로그인 화면에서는 `password_reset_required`가 일반 오류로 보인다(앱이 `invalid_credentials`로 합침). 이 화면이 유일한 셀프 복구 수단 |
| 탈퇴 계정 | 안 간다 | — | 탈퇴 때 이메일이 `withdrawn+<id>@deleted.invalid`로 바뀌고 토큰·가입 시도·세션이 지워진다. 원래 이메일로는 행이 없으므로 "가입 없음"과 같고, 같은 이메일로 다시 가입했다면 새 계정으로 처리된다. 익명 주소로는 메일이 갈 수 없다(`UNDELIVERABLE`) |
| 관리자 계정(`profiles.role`이 관리자) | 간다(API는 역할을 보지 않는다) | 일반 회원과 같다. 모든 세션 삭제(관리자 콘솔 로그아웃 포함) | 메일함 주인만 쓸 수 있으므로 허용을 권장한다(질문 2) |
| 메일이 일시적으로 보낼 수 없는 주소(없는 도메인 등) | 발송 실패, 응답은 같다 | — | 서버 로그에만 남는다. 화면에서 알 수 없다 |

### 4.3 미인증 계정을 재설정으로 확정할 때의 프로필 문제

가입 방해로 미인증 계정이 선점된 경우 `profiles`의 이름·연락처는 공격자가 먼저 넣은 값일 수 있다(가입 마무리 문서 3.2절 주의, 개인정보 B-1). 셀프 재설정은 이 경로를 일반 회원도 쓰게 만든다. 마이페이지에는 이름·연락처 수정이 없지만, 관리자 회원 상세 이름·연락처 수정 기능이 2026-11-26 배포되어 회원이 전화로 요청하면 바로 정정할 수 있다(처리방침 제6조 제2항, 가입 이메일로 본인 확인).

## 5. API 계약 (확정, 2026-11-26 backend-developer 구현 반영)

결론: **앱이 부르는 두 API의 요청·응답·오류 계약은 바뀌지 않았다.** 바뀐 것은 서버 내부 동작(재설정 성공 시 login-fail 해제, 알림 메일)과 메일 본문뿐이다. 앱은 호출 함수와 서버 액션만 새로 만든다(5.3). 구현 커밋: `feat(api): 비밀번호 재설정 완료 알림 메일, login-fail 해제, 메일 문구 보완`.

공통: 앱 서버 → API 호출. 헤더 `x-bara-service-key`(필수), `x-bara-client-ip`(회원 IP, 있으면 IP 제한 적용). 오류 본문은 `{ "error": { "code", "message", "field"? } }`.

### 5.1 `POST /v1/auth/request-reset` (계약 변경 없음)

| 항목 | 내용 |
|---|---|
| 요청 | `{ "email": string(1~254자, 이메일 형식, 앞뒤 공백 제거 후 소문자), "origin": string(SITE_ORIGINS 허용 목록 중 하나) }` |
| 200 | `{ "ok": true }` — 계정이 있든 없든, 이메일 제한(`reset-60s` 1회/60초, `reset-1h` 4회/1시간)에 걸렸든 같다(`auth-limits.test.ts` "상태·본문이 같고") |
| 400 | `{ error: { code: "validation", message: "요청 형식이 올바르지 않습니다.", field: "email" \| "origin" } }`. 허용되지 않은 origin도 `field: "origin"`(앱 설정 오류 → FP-ERR-FAILED) |
| 429 | `{ error: { code: "rate_limited", ... } }` — IP 제한 `reset-ip` 20회/1시간만. 이메일과 무관(FP-ERR-429) |
| 401 | `{ error: { code: "unauthorized_service" } }` 서비스 키 없음·틀림(앱 설정 오류 → FP-ERR-FAILED) |
| 503·연결 불가 | `code: "unavailable"`(DB 연결 불가 등) 또는 네트워크 오류. 앱이 `unavailable`로 매핑(FP-ERR-UNAVAILABLE). 그 밖의 5xx는 `failed` |
| 메일 | `recovery` 1통(제한 통과 + 계정 있을 때만), 링크 `{origin}/reset-password?token=`(1시간, 1회용). 응답 뒤 큐로 보내고 기다리지 않는다. 발송 실패는 응답에 영향 없음 |
| **변경** | `recovery` 메일 본문만 카피 문서 5.2(MAIL-RECOVERY-*)로 교체: "한 번만 쓸 수 있어요", 주소 복사 안내, 로그아웃 안내 추가. 제목·링크 형식은 그대로. 관리자 [재설정 메일 발송]도 같은 템플릿 |

### 5.1a `POST /v1/auth/reset-password` (계약 변경 없음, 동작 추가)

| 항목 | 내용 |
|---|---|
| 요청 | `{ "token": string(1~200자), "newPassword": string(8~200자) }` |
| 200 | `{ "ok": true }` → 앱은 `/sign-in?reset=1`로 이동 |
| 400 규칙 | `{ error: { code: "validation", message: "요청 형식이 올바르지 않습니다.", field: "password" \| "token" } }` (`newPassword` 오류는 `field: "password"`). 토큰은 소모되지 않아 다시 제출할 수 있다 |
| 400 토큰 | `{ error: { code: "validation", message: "invalid_token" } }` — 없음·만료·이미 사용·다른 용도 토큰을 구분하지 않는다(RP-EXPIRED-ERR) |
| 성공 시 서버 동작(기존) | 비밀번호 설정, 미인증이면 인증 완료, 그 회원의 모든 세션 삭제, 모든 메일 토큰 무효, 모든 가입 시도 삭제 |
| **추가 1** (대표 결정 5) | 같은 트랜잭션에서 그 이메일(소문자)의 `login-fail` 제한 기록을 삭제한다. 재설정 직후 새 비밀번호로 바로 로그인된다. 재설정이 롤백되면 기록도 남는다. `login-ip` IP 제한은 그대로다. 실패한 재설정(400)은 기록을 지우지 않는다 |
| **추가 2** (대표 결정 3) | 커밋 후 `password_changed` 알림 1통을 그 회원의 가입 이메일로 큐에 넣는다(카피 5.1, 링크 없음, `{at}`은 `profile_changed`와 같은 "2026년 11월 26일 오후 2시 12분" KST 형식). 응답은 발송을 기다리지 않고, 발송 실패는 200을 바꾸지 않는다(서버 로그 `auth mail failed`에 오류 이름만). 400이면 보내지 않는다 |

### 5.1b 메일 변경 요약 (API 내부, 앱 영향 없음)

| 메일 | 변경 | 비고 |
|---|---|---|
| `password_changed` | **신규** | 제목 "[바라 평생교육원] 비밀번호가 바뀌었어요". 담는 정보: 받는 사람 이메일, 바뀐 시각. 비밀번호·링크·이름·IP·기기 정보 없음. 문의처는 공통 블록(`SUPPORT_PHONE`·`SUPPORT_HOURS`) |
| `recovery` | 본문 변경 | 카피 5.2 |
| `already_registered` | 본문 변경 | 카피 5.3. `{origin}/forgot-password` 줄을 추가(HTML에서는 링크). `{origin}`은 가입 요청의 `origin`(SITE_ORIGINS 허용 목록 통과 값, 가입 인증·로그인 링크와 같은 출처)으로 채운다. 도메인을 코드에 적지 않는다. 카피 문서 6장 `{origin}` 항목 해소 |

### 5.2 이메일 열거 방지 점검

| 점검 항목 | 결과 |
|---|---|
| 응답 본문·상태 | 같다(위 테스트 보장) |
| 제한이 계정 존재 여부에 따라 달라지나 | 아니다. `reset-60s`, `reset-1h`, `reset-ip` 모두 계정 조회 전에 센다. 있는 이메일이든 없는 이메일이든 같은 횟수에서 같은 방식으로 걸린다. 429는 IP 기준이라 이메일에 의존하지 않는다 |
| DB 작업량 | 거의 같게 맞춰 두었다: 없는 계정은 조회 1회 + `reset-miss` 기록 1회, 있는 계정은 조회 1회 + 토큰 발급 1회. 테스트로 건수를 고정(`auth-limits.test.ts` "같은 DB 작업량") |
| 응답 시간 | 코드상 두 분기 모두 트랜잭션 1건(없는 계정: `reset-miss` insert, 있는 계정: 토큰 insert)이고, 메일은 `setImmediate`로 응답 뒤에 보내 기다리지 않는다. 이 비대기는 테스트로 보장한다(`auth-limits.test.ts` "메일 발송은 응답을 기다리지 않는다": 메일러를 막아 둔 채로 두 요청이 모두 응답함). 비밀번호 해시 같은 무거운 연산은 어느 분기에도 없다. **실제 응답 시간 분포는 재 보지 않았다**(2026-11-26 확인: 측정 테스트는 CI 환경 편차가 커서 넣지 않음). 한 이메일은 60초에 한 번만 이 분기를 타고 IP는 시간당 20회로 막혀 있어 시간 차이로 대량 열거하기는 어렵다. QA가 운영과 비슷한 환경에서 한 번 재 본다(5.4 E) |
| 화면 쪽 분기 | 서버 액션은 `200`이면 무조건 같은 "보냄" 상태를 돌려준다. 입력한 이메일을 그대로 되돌려 보여 주는 것 외에 서버 값을 쓰지 않는다 |
| 메일 도착 여부 | 가입된 주소의 주인만 알 수 있다. 이것은 막을 수 없는 정상 채널이다 |
| 기존 화면과의 차이 | 로그인 화면은 비밀번호가 맞은 사람에게만 "인증 전"을 보여 주고(열거 방지 문서 4장 방법 A), 이 화면은 비밀번호 없이 열리므로 어떤 계정 정보도 화면에 싣지 않는다 |

### 5.3 앱 쪽 변경 (frontend-developer, 코드 변경 필요 목록은 11장)

- `lib/db/auth.ts`의 `requestReset`을 `resend`처럼 `{ ok: true } | { ok: false, reason: 'rate_limited' | 'validation' | 'unavailable' | 'failed', field? }`로 넓힌다. 지금은 boolean이라 429를 구분하지 못한다.
- `app/actions/auth.ts`에 서버 액션 `requestPasswordReset`을 추가한다. `resendConfirmation`과 같은 구조(`isApiEmail` 검사 → 호출 → 상태 매핑). 성공이면 `{ requested: true, email }`.
- `AuthFormState`와 별개의 상태 타입이 필요하면 `{ error } | { requested: true, email } | undefined`로 둔다.

## 6. 엣지케이스 표

### 6.1 요청 단계

| 상황 | 동작 | 화면 |
|---|---|---|
| 가입된 이메일 | 제한 통과 시 메일 발송 | 보냄 |
| 가입 안 된 이메일 | 메일 없음 | 보냄(같음) |
| 탈퇴한 회원의 원래 이메일 | 메일 없음 | 보냄(같음) |
| 대문자·앞뒤 공백 입력 | 앱이 공백 제거, 서버가 소문자로 정규화 | 정상 |
| 형식이 틀린 이메일 | 서버 호출 없음 | 칸 아래 안내 |
| 같은 이메일로 60초 안에 재요청 | 메일 없음(두 번째는 막힘), 응답은 같음 | 보냄. 다시 받기 버튼은 60초 비활성 |
| 한 시간에 5번째 요청 | 메일 없음, 응답 같음 | 보냄 |
| 같은 IP에서 21번째 요청 | 429 | 횟수 초과 안내, 입력 유지 |
| 같은 이동통신·공용 와이파이 IP에서 여러 사람이 요청 | IP 제한(시간당 20회)을 같이 쓴다 | 횟수 초과. "잠시 후 다시"로 안내. 학원 PC 사용 환경이면 질문 필요 시 한도 조정(현재 기준 낮은 위험으로 본다) |
| 남이 내 주소로 계속 요청(괴롭힘) | 시간당 4통까지 내 메일함에 도착. 그 뒤는 막힘 | 본인에게는 "무시해도 돼요" 안내가 메일에 있다 |
| 남이 내 주소의 재설정 한도를 먼저 써서 내 요청이 막힘 | 내 요청은 메일 없이 200. 이미 도착한 메일 링크(1시간 유효)를 쓰면 된다. 그 시간이 지나면 한도가 풀릴 때까지 기다린다 | 보냄. 안 오면 전화 문의 |
| 앱 → API 연결 불가 | 503 | 연결 불가 안내, 입력 유지 |
| 허용되지 않은 origin(설정 오류) | 400 | 기타 실패 안내 |
| 로그인 상태에서 접속 | 막지 않는다 | 같은 화면 |
| 가입 방해 중(공격자 가입 시도 N개) | 가입·재전송 한도와 별개로 재설정 메일이 간다 | 보냄 |
| 이메일 칸 자동 완성으로 다른 사람 주소가 채워짐 | 사용자가 확인하도록 보냄 화면에 입력한 주소를 보여 준다 | 보냄 |

### 6.2 링크 사용 단계

| 상황 | 동작 | 화면 |
|---|---|---|
| 정상 사용 | 비밀번호 설정, 인증 완료(미인증이었다면), 모든 세션·토큰·가입 시도 삭제 | `/sign-in?reset=1` |
| 1시간 지난 링크 | 400 `invalid_token` | 3장 만료 오류 + 다시 요청 링크 |
| 이미 쓴 링크, 또는 다른 링크로 먼저 바꾼 뒤 남은 링크 | 같음 | 같음 |
| 링크를 여러 번(최대 4개) 받음 | 하나를 쓰면 나머지는 모두 무효. 가장 최근 메일이 아니어도 된다 | 정상 |
| 메일 스캐너가 링크를 먼저 열음 | GET은 토큰을 쓰지 않는다 | 정상(토큰은 남아 있음) |
| 링크가 잘려 열림(메일 앱 줄바꿈) | 토큰 없음 또는 오류 | 3장 토큰 없음 화면 + 다시 요청 링크. 메일에는 "링크가 열리지 않으면 주소를 복사해 붙여 넣어 주세요"가 없으므로 D(5.4)처럼 한 줄 추가를 권장 |
| 다른 기기·인앱 브라우저에서 열음 | 토큰과 새 비밀번호로 완결. 쿠키에 의존하지 않는다 | 정상 |
| 새 비밀번호가 8자 미만·두 칸 불일치 | 서버 호출 전 안내 | 칸 위 오류 |
| 제출 중 연결 오류 | 입력 유지 | 연결 불가 안내(권장) |
| 더블 탭 | 버튼 비활성. 두 번째 요청은 400이 될 수 있다 | 첫 요청이 redirect하므로 보통 보이지 않는다 |
| 성공 후 로그인 제한에 걸림 | 재설정 성공 시 그 이메일의 `login-fail` 기록을 지운다(대표 결정 5, 5.1a) | 새 비밀번호로 바로 로그인. 같은 IP의 `login-ip`(50회/15분)는 남는다 |

### 6.3 가입 방해 시나리오와의 관계

| 상황 | 동작 |
|---|---|
| 공격자가 피해자 이메일로 재가입을 반복해 가입 링크가 밀려난 피해자 | 이 화면에서 재설정 메일을 받는다. 재설정 한도는 가입·재전송 한도와 분리되어 있어 영향받지 않는다 |
| 공격자가 피해자 이메일로 재설정을 반복 요청 | 시간당 4통 한도. 피해자는 어느 링크로든 쓸 수 있고, 링크를 쓰면 공격자의 가입 시도가 모두 삭제된다 |
| 공격자가 재설정 링크를 가로챔 | 메일함을 장악하지 않는 한 불가능. 장악했다면 이메일 본인 확인 정책의 한계다(대표 결정 2026-11-26) |
| 피해자가 재설정으로 계정을 확정한 뒤 공격자가 같은 이메일로 다시 가입 | 이미 인증된 계정이므로 "이미 가입된 계정" 안내 메일만 간다. 공격자는 아무것도 바꿀 수 없다 |

### 6.4 이 화면으로 해결하지 못하는 경우 (알려진 한계)

| 상황 | 현재 가능한 것 |
|---|---|
| 가입한 이메일의 메일함에 접근할 수 없다(주소 변경·폐쇄·계정 잠김) | 이 화면으로 불가. 관리자도 같은 가입 이메일로만 재설정 메일을 보내므로 불가. 이메일 변경 기능은 없다 |
| 가입 때 이메일을 잘못 써서 계정이 남의 주소(또는 없는 주소)로 만들어짐 | 불가. 새 이메일로 다시 가입해야 한다(수강 이력 이관 없음) |
| 메일이 계속 스팸함으로 감 | 안내 문구만 제공 |

이메일 변경·본인 확인 수단을 늘릴지는 이번 범위 밖이며 질문 9에 기록한다.

## 7. 접근성 (시니어·해외이주민 포함)

| 항목 | 정의 |
|---|---|
| 글자·터치 | 입력 칸·버튼은 가입 마무리 화면의 `lg` 크기(높이 56px 이상, 본문 16px 이상)를 쓴다. 한 화면에 입력 한 칸과 버튼 하나만 둔다 |
| 라벨 | 이메일 칸에 보이는 `<label>`("가입한 이메일")을 쓴다. placeholder만으로 두지 않는다. 보조문은 `aria-describedby`로 연결한다 |
| 입력 | `autocomplete="email"`, `inputMode="email"`, `autocapitalize="none"`, `spellcheck="false"` |
| 오류 | 오류는 칸 아래에 아이콘 + 글로 보여 주고 `aria-invalid`와 `aria-describedby`로 칸에 연결한다. 색만으로 구분하지 않는다. 제출 뒤 오류가 있으면 이메일 칸으로 포커스를 옮긴다 |
| 상태 알림 | 보냄 화면으로 바뀌면 제목으로 포커스를 옮기고 `aria-live="polite"` 영역에서 한 번 읽어 준다. 429·연결 불가 알림은 `role="alert"` |
| 카운트다운 | 60초 카운트는 초마다 읽지 않는다. "1분 뒤에 다시 받을 수 있어요"를 시작 때 한 번, 활성화될 때 "이제 다시 받을 수 있어요"를 한 번만 알린다. 버튼은 `aria-disabled`와 이유 텍스트를 함께 둔다 |
| 키보드 | 모든 동작이 탭·엔터로 된다. 포커스 링은 기존 `FOCUS_RING`을 쓴다 |
| JS 없이 | `<form action>` 서버 액션으로 제출되고 첫 화면은 서버 렌더(인앱 브라우저 대비). 카운트다운이 없으면 다시 받기 버튼은 활성 상태로 두고 서버 한도가 막는다 |
| 문구 | 쉬운 `~해요`체, 한 문장에 할 일 하나. "재설정", "링크" 같은 말은 처음 나올 때 풀어 쓴다("비밀번호를 새로 정하는 링크"). 이모지·느낌표 없음. 번역·읽어 주기 도구가 잘 처리하도록 약어를 쓰지 않는다 |
| 전화 안내 | 전화번호는 `tel:` 링크(`PhoneButton` 패턴)로 하고 운영시간(`siteConfig.supportHours`)을 같이 적는다. 번호는 하드코딩하지 않는다 |
| 재설정 화면 | 새 비밀번호 두 칸에 [보기]/[숨기기] 토글(3장), 확인 칸이 틀리면 칸 아래에 즉시 안내 |
| 메일 | 텍스트 본문에 링크를 한 줄로 둔다(기존 SES 템플릿 형식). 링크가 안 열릴 때 복사 안내 |

## 8. 개인정보 영향 (privacy-security-officer 검토 요청)

| 항목 | 내용 |
|---|---|
| 새로 받는 정보 | 이메일 주소 1개. 가입된 회원의 주소이거나, 회원이 아닌 제3자가 입력한 주소일 수 있다 |
| 저장되는 곳 | 계정이 있을 때만 `auth.email_tokens`(토큰 해시, 사용자 id, 1시간 유효). 회원이 아닌 주소는 어디에도 저장하지 않는다. 다만 제한 기록 `auth.rate_events`의 `key`에 입력한 이메일이 그대로 들어가고 25시간 보관된다(`rate-limit.ts` `RETENTION_SECONDS`). 가입·재전송과 같은 기존 방식이지만 비회원 주소가 포함되므로 보관 기간 적정성 확인 요청 |
| 화면·로그 | 이메일을 URL·쿼리에 싣지 않는다(질문 6). 서버 액션과 앱 로그에 이메일을 남기지 않는다(오류 로그에도 종류만). 보냄 화면은 방금 입력한 주소를 입력한 사람에게만 되돌려 보여 준다 |
| 토큰 | 재설정 링크의 토큰은 URL에 있으므로 `/reset-password`에 no-referrer·no-store·noindex 헤더를 건다(3장) |
| 제3자 | 메일 발송은 기존과 같은 Amazon SES를 쓴다. 처리방침의 위탁 업무에 "비밀번호 재설정 메일 발송"이 이미 있어 새 위탁은 없다(확인 요청) |
| 목적 외 이용 | 입력한 이메일로 마케팅·다른 용도의 메일을 보내지 않는다 |
| 본인 확인 | 이메일 소유 확인만 한다. 휴대폰 본인인증을 추가하지 않으므로 휴대폰번호를 새로 받지 않는다(대표 결정 2026-11-26) |
| 이용자 괴롭힘 | 제3자가 남의 주소로 재설정 메일을 보내게 할 수 있다. 시간당 4통·IP 20회 한도와 "요청하지 않았다면 무시해 주세요" 안내로 줄인다 |
| 계정 탈취 | 메일함을 장악한 사람은 비밀번호를 바꿀 수 있다. 완화책은 재설정 완료 알림 메일(5.4 C)과 모든 세션 삭제(이미 구현) |
| 처리방침 | 새로 받는 항목이 없어 개정은 필요 없다고 본다. 위 `rate_events` 보관과 알림 메일(C)을 도입할 때는 officer 확인 후 결정 |
| 관리자 접근 기록 | 셀프 재설정은 관리자가 개인정보를 열람하는 동작이 아니므로 `logAdminAccess` 대상이 아니다. 단 서버에 "재설정 요청·완료" 이벤트를 남길지는 backend-developer와 officer가 정한다(이메일 원문은 남기지 않는다) |

## 9. 문구 초안 (최종 문구는 ux-writer가 정한다)

### 9.1 `/forgot-password`

| 위치 | 초안 |
|---|---|
| 제목 | 비밀번호 찾기 |
| 안내 | 가입한 이메일 주소를 입력하면, 비밀번호를 새로 정하는 링크를 보내 드려요. |

## 10. 대표 확인이 필요한 정책 (추천안 포함)

1. 보냄 화면 문구: 가입 여부를 단정하지 않는 조건 문구(9.2 본문 A, "가입한 이메일이 맞다면 …도착해요")로 할지, 가입 화면과 같은 단정형(본문 B, "안내 메일을 보냈어요")으로 할지.
   - 추천: A. B는 가입되지 않은 주소에는 메일이 가지 않아 사실과 다르다. A는 열거 위험이 같고(모든 경우에 같은 문구) 거짓이 없다. 가입 화면 문구와 어긋나는 점은 ux-writer가 용어를 맞춘다.
2. 관리자 계정도 이 화면으로 재설정 메일을 받게 할지(현재 API는 구분하지 않는다).
   - 추천: 허용. 메일함 주인만 쓸 수 있고, 막으면 관리자가 비밀번호를 잊을 때 다른 관리자 도움이 필요해진다. 열거 방지를 위해 막는다면 화면은 같게 두고 메일만 안 보내는 방식이 된다. 성공 시 관리자 세션도 모두 끊기는 점은 같다.
3. 재설정 완료 알림 메일("비밀번호가 바뀌었어요. 본인이 아니면 전화해 주세요")을 도입할지(5.4 C).
   - 추천: 도입. 메일함 침해를 본인이 알 수 있는 유일한 사후 장치이고 비용은 템플릿 1종이다. 이번 배포를 막을 만큼은 아니므로 후속 배포도 가능. 처리방침의 위탁 범위(재설정 메일)에 들어가는지 officer 확인.
4. 재설정 링크 읽기 전용 확인 API(5.4 B)를 이번에 포함할지.
   - 추천: 이번에는 보류하고 만료 오류 화면에 [재설정 메일 다시 받기]를 붙이는 것(3장)까지만 한다. 가입 마무리 화면처럼 열자마자 만료를 알려 주는 개선은 후속. 시니어가 입력한 뒤 실패하는 불편은 있지만 다시 요청하는 길은 열린다.
5. 비밀번호를 여러 번 틀려 로그인 제한에 걸린 사람이 재설정을 마친 뒤 제한을 풀지(5.4 A).
   - 추천: 푼다(재설정 성공 시 그 이메일의 `login-fail` 기록 삭제). 풀지 않는다면 성공 배너에 "로그인이 막히면 15분 뒤에 다시 해 주세요"를 넣는다.
6. 이메일을 URL로 미리 채워 주는 것(로그인 화면 → 비밀번호 찾기)을 할지.
   - 추천: 하지 않는다. 주소가 접근 로그·기록에 남고, 입력 한 번이 크게 어렵지 않다. 시니어 편의가 중요하면 입력 칸 `autocomplete="email"` 자동 완성에 맡긴다.
7. 가입 방해 복구(미인증 계정 확정) 뒤 프로필의 이름·연락처가 공격자 값일 수 있는 문제(4.3절). → 관리자 수정 기능이 이미 배포(2026-11-26)되어 해소. 전화 정정으로 처리.
   - 추천: 이 화면은 먼저 배포해도 된다(복구 수단이 없는 지금보다 낫다). 단 정정 요구는 전화로 받는 것을 응대 안내에 포함하고, 관리자 수정 기능 일정은 유지한다.
8. 가입 마무리의 `locked`·`expired` 화면과 "기억나지 않아요" 영역에서 [비밀번호 새로 정하기]를 [처음부터 다시 가입하기]보다 앞세울지.
   - 추천: 앞세운다. 재가입은 새 시도·새 메일이 늘고 한도·5개 상한 위험(가입 마무리 문서 위험 감수 기록)이 있지만, 재설정은 공격자의 모든 가입 시도를 삭제하고 한도도 따로 쓴다. 이 변경은 가입 마무리 문서의 5.2절·7장·2.1절과 맞춰야 한다.
9. (참고) 가입한 이메일의 메일함을 쓸 수 없는 회원의 복구 수단(이메일 변경)은 이번 범위 밖으로 두는지. 현재 정책(이메일만으로 확인)에서는 해결 방법이 없다.
   - 추천: 범위 밖. 수요가 확인되면 별도 기획한다.

- 이 화면에는 채운 인디고 버튼이 없다. 사용자의 다음 행동은 앱 밖(메일함)이라 앱 안에서 누를 주 행동이 없기 때문이다. 대신 [다시 받기]를 윤곽선으로 두어 "아직 더 할 일이 있는 것처럼" 눈길을 빼앗지 않게 한다.
- [다시 받기 버튼]은 60초 동안 `aria-disabled=true`(스크립트가 클릭을 막음, `disabled`는 쓰지 않아 포커스를 잃지 않음). 버튼 안 글자는 [다시 받기 버튼]만 두고, 남은 시간은 `#resend-hint` 옆에 숫자 텍스트로 눈에만 보이게 갱신한다(`aria-hidden`). 시각적으로는 `opacity-60`과 `cursor-not-allowed`, 테두리 색 유지.

- JS가 없으면 카운트가 없고 버튼은 활성이다(정의서 7장). 서버 한도가 막는다.

#### P-1.4 오류 상태 (입력 유지, 포커스 규칙은 P-5)

| 상태 | 위치와 모양 | 포커스 | 동작 |
|---|---|---|---|
| 칸 비어 있음 / 형식 오류 (클라이언트, 서버 호출 없음) | 칸 바로 아래 `p#forgot-email-error`: `AlertIcon size-5 text-danger` + [칸 오류 문구], `text-base text-n-9`. 칸은 `aria-invalid=true`(`INPUT_LG`가 빨간 테두리 처리) | 이메일 칸 | 제출 시와 blur 시. 입력을 고치기 시작해도 제출 전까지 유지하고, 다음 제출에서 재평가 |

- 429와 연결 불가는 모양이 같고 문구만 다르다. 시니어에게 상태 종류를 색·아이콘으로 나누면 오히려 혼란스럽다(가입 마무리 `failKind` 알림과 같은 판단).
- 서버 오류 알림은 폼 위, 칸 오류는 칸 아래로 두 층을 나눈다. 동시에 둘이 뜨는 일은 없다(형식 오류는 서버를 부르지 않으므로).
- 서버 액션이 돌려준 오류 상태는 JS가 없어도 그려지도록 서버 렌더에서도 같은 마크업으로 나온다.

### P-2. `/reset-password` 변경분 (`ResetPasswordForm.tsx`)

현재 이 폼은 13px 칸·`bg-pink` 버튼·12.5px `text-danger`라 새 요구(시니어·대비)와 어긋난다. 이번에 손대는 화면이므로 **같은 파일에서 large 계열로 맞출 것을 권장한다**(가입 마무리 V-0 #1이 "새로 만들거나 손대는 화면은 큰 글씨"로 한 것과 같은 원칙). 범위를 줄이려면 아래 (a)(b)(c)(d)만 하고 크기 정리는 후속으로 둔다. 이 경우 후속 TBD를 남긴다.

```
h1  (페이지의 기존 제목 유지, TITLE 클래스 정렬은 page.tsx에서)
```

- (a) 보기/숨기기: `PasswordField`를 그대로 재사용한다(새 컴포넌트 없음). 두 칸이 같은 `shown`을 공유한다. 제출 때 `setShown(false)`로 숨김으로 되돌린다(`AuthForm`과 같음).

#### P-2.1 토큰 없음·형식 오류 (현재 `!token` 분기)

`SignupLinkStatus`의 `expired/invalid` 틀을 따른다: 원형 아이콘 칸(`ClockIcon`) + h1(`tabIndex=-1`) + 본문 [링크 오류 본문] + 아래 버튼 영역.
- 버튼 영역: `Link href="/forgot-password"` **`PRIMARY_BTN`**: [재설정 메일 다시 받기] (채운 버튼 1개), 그 아래 `LINK_CLASS` [로그인 화면으로].
- 현재의 빨간 글씨 한 줄은 쓰지 않는다(`danger` 본문색 미달).

#### P-2.2 만료·이미 사용·잘못된 토큰 (제출 뒤 `invalid_token`)

폼은 그대로 두고(입력 유지) 폼 맨 위에 `notice-danger role="alert"`: [만료 오류 본문]. 그 알림 **안쪽 맨 아래**에 `Link href="/forgot-password"`를 `SECONDARY_BTN`으로 둔다: [재설정 메일 다시 받기].
- 이유: 이 상태에서 사용자가 진짜 할 일은 새 링크를 받는 것인데, 아래의 [비밀번호 변경] 채운 버튼이 같은 힘으로 보이면 만료된 링크로 다시 눌러 같은 오류를 반복한다. 그래서 알림 안의 링크를 윤곽선 버튼으로 크게 두고, 제출 버튼은 유지하되 채운 버튼이 둘이 되지 않게 한다(링크는 윤곽선, 제출은 채움).
- 이 오류가 뜨면 포커스는 알림으로 옮기지 않는다(`role=alert`가 읽는다). 단, 알림 안 링크가 첫 탭 대상이 되도록 DOM 순서를 알림 → 폼 칸 순으로 둔다.
- 연결 불가(503)는 `notice-danger`에 [연결 불가 안내]만, 링크 없음. 입력 유지.

### P-3. 진입점 링크 배치

### P-4. 모바일 360px

- 카드 폭: 360 - 48(`px-6`) = **312px**. 입력·버튼 `w-full` 312px. 데스크톱에서도 `max-w-[440px]`(칸 폭 변화 없음).
- 칸 높이 56px(`h-14`), 버튼 `min-h-14`(문구가 2줄이 되면 늘어난다). 글씨 칸·버튼 16px 이상(iOS 확대 방지).
- 터치 영역: 모든 링크 `min-h-11`(44px), 인접 터치 대상 간격 8px 이상(`gap-3`). `PasswordField`의 [보기] 토글은 `h-12 min-w-[60px]`(이미 충족).
- 제목 `text-2xl`(24px), 줄 수 2줄 이내 가정. `break-keep`로 어절 단위 줄바꿈. 이메일은 `break-all`(보냄 화면 본문, 길면 3줄까지 허용).
- 전화 버튼 번호 `whitespace-nowrap text-xl`(기존)이 312px에서 넘치지 않는지 확인(가입 마무리와 같은 마크업이라 통과 가정, 360px 스크린샷 확인 필요).
- 가로 스크롤 없음. 키보드가 올라와도 버튼이 가려지지 않도록 하단 고정 요소 없음. 보냄 화면 전체 길이는 한 화면을 넘길 수 있고(스팸함 목록·전화 영역) 세로 스크롤은 허용. 제목과 [다시 받기]는 첫 스크롤 없이 보여야 한다(안 올 때 목록은 그 아래).
- 확대(200%)·큰 글씨 설정에서 버튼 문구가 잘리지 않게 `min-h`만 쓰고 `h-`로 고정하지 않는다.

### P-7. 확인·결정이 필요한 점과 사용성 위험

1. 가입 마무리 `<details>` 안에서 [비밀번호 새로 정하기]를 채운 버튼으로 둘지(위 P-3). 안 A(권장): `<details>` 안 첫 버튼을 `SECONDARY_BTN`으로 두고 [처음부터 다시 가입하기]를 텍스트 링크로 낮춘다. 폼의 [가입 완료하기]가 유일한 채운 버튼으로 남는다. 안 B: 채운 버튼으로 둔다(대표 결정 8을 가장 강하게 반영하지만 한 화면 채운 버튼 2개). `locked` 화면은 [가입 완료하기]가 없으므로 어느 안이든 채운 버튼으로 둔다.
2. `expired·invalid`에서 재설정을 채운 버튼으로 올릴지(위 P-3). 권장은 메일 다시 받기를 채운 버튼으로 유지(링크가 만료됐을 뿐 비밀번호를 잊었다는 증거는 없다)하고 재설정은 바로 아래 한 줄로 둔다. 대표 결정 8의 "먼저"를 문자 그대로 적용하려면 순서만 바꾼다.
3. `/reset-password`를 large 계열로 전면 정리할지, 필요한 4가지(보기·안내·오류 링크·autocomplete)만 할지. 권장은 전면 정리(작은 글씨·핑크 버튼 폼에 큰 글씨 칸이 섞이는 것이 더 어색하다).
4. 이 화면이 `AuthForm`의 로그인 오류 알림(12.5px `text-danger`, 미달)과 한 흐름으로 이어진다. 로그인 쪽의 대비·크기 정리는 이번 범위 밖(가입 마무리 V-9와 같은 제안). 로그인에 링크만 추가한다.
5. 보냄 화면에서 "가입된 이메일이 맞다면"의 조건 문구는 불안을 키울 수 있다. 문구 쪽(ux-writer)에서 "메일이 오지 않을 때"를 바로 이어 보이도록 위 레이아웃의 순서(본문 → 유효시간 → 안 올 때 목록)를 유지한다.
6. 60초 카운트다운은 스크린리더·JS 없는 환경에서 가장 깨지기 쉬운 부분이다. QA에서 TalkBack·VoiceOver로 시작·종료 안내가 각각 한 번인지 확인한다(F8 이후).
