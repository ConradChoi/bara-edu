# 관리자 회원 정보 수정(이름·연락처) — 최종 문구 (카피 문서)

- 작성일: 2026-11-26
- 작성: ux-writer
- 근거: `bara-edu-lms.admin-profile-edit.md` 맨 끝 '결정(ceo-advisor 위임 판단)'. 그 문서 10장의 초안을 이 문서가 대체한다. 결정과 다른 곳은 없다.
- 말투: 쉬운 `~해요`체. "해 주세요"처럼 띄어 쓴다. 이모지·느낌표 없음. 사용자를 탓하지 않고, 오류에는 "무엇이 안 됐는지 + 다음에 할 일"을 넣는다.
- 범위: 문구만. 코드는 바꾸지 않았다. `{ }`는 화면이나 서버가 채우는 값이다.
- 전화번호와 운영시간은 하드코딩하지 않는다. 앱은 `siteConfig.phone`·`siteConfig.supportHours`, API 메일은 `api/src/mail/support.ts`의 `SUPPORT_PHONE`·`SUPPORT_HOURS`를 쓴다. 현재 값은 `010-9025-5093`, `평일 10:00~18:00(점심 11:30~13:00 제외)`이다.
- 미확정: Q4(수료증을 종이·PDF로 따로 드리는지)는 대표 확인 대기다. 4.2의 수료증 안내는 어느 답이어도 사실과 맞게 썼다.

## 0. 용어 (이 기능 전용)

| 용어 | 쓰는 곳 | 쓰지 않는 말 |
|---|---|---|
| 이름·연락처 수정 | 관리자 버튼, 기능 이름 | 정보 변경, 프로필 편집, 정정 처리 |
| 휴대전화 | 입력칸 라벨, 이력, 메일 항목명, 마이페이지 | 전화번호(스크립트 속 말하기는 예외), 핸드폰, 연락처(라벨에서) |
| 고치는 이유 | 사유 선택칸 라벨 | 정정 사유, 변경 사유 |
| 본인 확인 | 체크 문구 | 인증, 신원 확인 |
| 가입 이메일 | 본인 확인 기준 | 아이디, 계정 이메일 |
| 정보 수정 이력 | 이력 섹션 제목 | 변경 로그, 감사 기록 |
| 안내 메일 | 회원에게 가는 메일 | 알림, 통지서 |
| 가입 마무리 전 | 수정 불가 이유 | 미인증 (기존 용어집과 같음) |

- 버튼 이름은 "이름·연락처 수정", 칸 라벨은 "휴대전화"로 둔다. 버튼은 이름과 연락처를 묶어 부르는 말이고, 칸 라벨과 메일 항목명은 회원이 마이페이지에서 보는 "휴대전화"와 맞춘다. 같은 항목이 화면마다 다른 이름이 되지 않게 한다.
- 관리자 화면이라 존댓말은 '~해요'체로 통일한다. 정의서의 "회원님"은 메일에서만 쓴다.

## 1. 관리자 화면: 편집

위치: `app/(admin)/admin/members/[id]/page.tsx` 기본 정보 카드 (`MemberProfileEditor`).

### 1.1 버튼과 안내

| 위치 | 문구 |
|---|---|
| 보기 상태 버튼 | 이름·연락처 수정 |
| 편집 상단 안내 | 회원에게 가입 이메일 `{email}`로 본인 확인을 마친 뒤에 고쳐 주세요. |
| 주 버튼 | 변경 내용 확인 |
| 보조 버튼 | 취소 |
| 변경 없음(버튼 비활성 + 칸 아래) | 바뀐 내용이 없어요. |

### 1.2 입력칸

| 위치 | 문구 |
|---|---|
| 이름 라벨 | 이름 |
| 이름 도움말 | 2자 이상 100자 이하로 입력해 주세요. |
| 휴대전화 라벨 | 휴대전화 |
| 휴대전화 도움말 | 숫자, 공백, -, +, ( )만 쓸 수 있어요. 비워 두면 휴대전화가 지워져요. |
| 휴대전화 입력 예시(placeholder) | 010-1234-5678 |

- 이름 도움말은 정의서의 "입력해요"를 "입력해 주세요"로 바꿨다. 입력 요청이라 요청형이 맞다.
- 해외 번호(+국가번호)도 받으므로 도움말에 "+"를 넣었다. 예시는 한국 번호 하나만 둔다.

### 1.3 고치는 이유(필수, 기본 선택 없음)

| 위치 | 문구 |
|---|---|
| 라벨 | 고치는 이유 |
| 안 골랐을 때 칸 안 문구 | 이유를 골라 주세요 |
| 선택지 1 | 회원 요청 |
| 선택지 2 | 오기 정정 |
| 선택지 3 | 가입 때 다른 사람이 입력한 값 정정 |
| 선택지 4 | 기타 |
| 메모 라벨 | 메모 (기타를 고르면 꼭 적어 주세요) |
| 메모 도움말 | 이름이나 전화번호는 적지 말아 주세요. 접속 기록에 1년 동안 남아요. |

선택지 3 옵션

| 옵션 | 문구 | 뉘앙스 |
|---|---|---|
| A (권장) | 가입 때 다른 사람이 입력한 값 정정 | 상황이 정확하다. 이력에 남으므로 짧고 중립적이다. |
| B | 가입 때 남이 입력한 값 정정 | 정의서 초안. "남"이 거칠게 읽힌다. |
| C | 가입 시도 값 정정 | 짧지만 "시도 값"이 운영자에게도 낯설다. |

### 1.4 본인 확인 체크(필수)

| 위치 | 문구 |
|---|---|
| 체크 문구 | 회원에게 가입 이메일로 본인 확인을 마쳤어요. |
| 안 체크했을 때 | 본인 확인을 마친 뒤에 체크해 주세요. |

- 체크 문구는 사실을 적는다. 체크는 "책임 기록"이므로 "확인했습니다"처럼 서명하는 말투 대신 평소 말투로 쓴다.
- 전화 응대에서 확인하는 것은 가입 이메일뿐이다. 이름·연락처는 확인 기준으로 쓰지 않으므로 체크 문구에도 넣지 않는다.

## 2. 관리자 화면: 확인 단계

| 위치 | 문구 |
|---|---|
| 제목 | 아래 내용으로 바꿀까요? |
| 이름 읽기 안내(이름이 바뀔 때, 큰 글씨 이름 위) | 바뀌는 이름을 회원에게 한 번 더 읽어 드려 확인해 주세요. |
| 표 머리 | 항목 / 변경 전 / 변경 후 |
| 안 바뀐 항목 | 변경 없음 |
| 휴대전화를 비울 때 | (비움) |
| 요약 줄 | 고치는 이유: `{이유}` / 본인 확인: 가입 이메일로 마쳤어요 |
| 이름 변경 영향 안내 | 이름이 바뀌면 신청 내역, 수료 이력, 수료 관리 화면에 바뀐 이름으로 보여요. |
| 입금 대기 경고(대기 신청 N건 이상일 때) | 입금 대기 중인 신청이 `{N}`건 있어요. 승인할 때 입금자명이 바뀐 이름과 맞는지 확인해 주세요. 회원이 이전 이름으로 입금해도 되는지도 안내해 주세요. |
| 수료증 안내(수료 이력 N건 이상일 때) | 수료 이력이 `{N}`건 있어요. 수료증은 바뀐 이름으로 보여요. 이미 종이나 파일로 드린 수료증이 있으면 이름이 다를 수 있어요. |
| 안내 메일 알림 | 저장하면 `{email}`로 변경 안내 메일이 가요. 바뀐 값은 메일에 적지 않아요. |
| 주 버튼 | 저장 |
| 보조 버튼 | 돌아가서 고치기 |
| 저장 중(버튼) | 저장하는 중이에요 |

- 입금 대기 경고를 "승인할 때 확인"과 "이전 이름 입금 안내" 두 가지 할 일로 나눴다. 정의서 6장의 의도(대기 신청이 걸린 회원이 이전 이름으로 입금하면 승인 때 혼선이 생긴다)를 그대로 옮겼다.
- 이름이 안 바뀌고 휴대전화만 바뀌면 "이름이 바뀌면…" 영향 안내, 입금 대기 경고, 수료증 안내는 보이지 않는다.
- 경고는 노란 정보 상자로 둔다. 저장을 막는 문구가 아니라 알려 주는 문구라서 색을 낮춘다.
- 수료증 안내는 Q4와 무관하게 사실이다. 시스템 화면은 바뀐 이름으로 보이고, 밖에서 드린 수료증은 이름이 다를 수 있다. 재발급 여부를 단정하지 않는다.

## 3. 관리자 화면: 결과와 오류

위치: 페이지 상단 배너 또는 해당 칸 아래. 기존 `success`/`error` 배너 패턴을 쓴다.

### 3.1 성공

| 상황 | 문구 |
|---|---|
| 성공(메일 접수) | 이름·연락처를 수정했어요. 가입 이메일로 안내 메일을 보냈어요. |
| 성공(이름만) | 이름을 수정했어요. 가입 이메일로 안내 메일을 보냈어요. |
| 성공(휴대전화만) | 휴대전화를 수정했어요. 가입 이메일로 안내 메일을 보냈어요. |
| 성공 + 메일 불확실(노란 보조 배너) | 수정은 끝났어요. 다만 안내 메일을 보내지 못했을 수 있어요. 회원에게 전화로 한 번 알려 주세요. |
| 변경 없음(서버가 unchanged) | 바뀐 내용이 없어요. 저장하지 않았어요. |

- 성공 문구는 정의서 초안 "이름·연락처를 수정했어요."에 메일 사실을 붙였다. 운영자가 "메일이 갔다"를 믿고 전화로 안내를 건너뛸 수 있으므로, 메일 불확실 배너는 전화 안내를 할 일로 적었다.
- 바뀐 항목명은 `changed` 값으로 고른다(이름·연락처 / 이름 / 휴대전화). 항목이 둘이면 앞의 첫 문구를 쓴다.
- 메일은 대기열 방식이라 "보냈어요"는 "보내기를 접수했어요"와 같다. 접수가 확인된 경우(`mailQueued: true`)에만 쓴다.

### 3.2 칸 검증 오류 (칸 아래 한 줄, `role="alert"`)

| 칸 | 상황 | 문구 |
|---|---|---|
| 이름 | 비어 있음·1자·101자 이상·제어 문자 | 이름은 2자 이상 100자 이하로 입력해 주세요. |
| 이름 | `탈퇴한 회원` | 이 이름은 쓸 수 없어요. 다른 이름을 입력해 주세요. |
| 휴대전화 | 문자·길이 위반 | 휴대전화는 숫자 7개 이상, 30자 이하로 입력해 주세요. 숫자, 공백, -, +, ( )만 쓸 수 있어요. |
| 휴대전화 | `*` 포함(서버 `phone_masked`) | 가려진 번호는 저장할 수 없어요. 회원에게 받은 번호 전체를 입력해 주세요. |
| 이유 | 안 고름 | 고치는 이유를 골라 주세요. |
| 메모 | 기타인데 5자 미만 | 기타를 고르면 메모를 5자 이상 적어 주세요. |
| 메모 | 100자 초과 | 메모는 100자 이하로 적어 주세요. |
| 메모 | 개인정보 형태(서버 `memo_has_pii`) | 메모에는 이름이나 전화번호를 적지 말아 주세요. |
| 본인 확인 | 미체크 | 본인 확인을 마친 뒤에 체크해 주세요. |

- 오류는 칸에서 벗어날 때(blur)와 `[변경 내용 확인]`을 누를 때 보여 준다. 입력하는 도중에는 띄우지 않는다.
- 이름·전화·메모의 허용 범위는 정의서 1.4와 3.2의 규칙 그대로다.

### 3.3 409·서버·연결 오류

| 상황 | 위치 | 문구 |
|---|---|---|
| 409 `stale`(다른 관리자가 먼저 고침) | 편집 상단 배너, 폼은 최신 값으로 채움 | 다른 관리자가 먼저 고쳤어요. 최신 내용으로 다시 불러왔어요. 한 번 더 확인해 주세요. |
| 409 `withdrawn`, `not_confirmed`(편집 중 상태 바뀜) | 상단 배너, 보기 화면으로 | 그 사이 회원 상태가 바뀌어 저장하지 못했어요. 화면을 새로 열었어요. 아래 안내를 확인해 주세요. |
| 409 `target_is_admin` | 상단 배너 | 운영자 계정은 이 화면에서 고칠 수 없어요. |
| 403 | 상단 배너 | 관리자 권한이 필요해요. 권한이 있는 계정으로 로그인해 주세요. |
| 401 | 로그인 화면으로 이동 | (화면 이동. 로그인 화면의 기존 만료 문구를 따른다) |
| 503 `log_failed`(접속 기록 실패) | 확인 단계 위 | 접속 기록을 남기지 못해서 저장하지 않았어요. 입력한 내용은 그대로예요. 잠시 후 다시 눌러 주세요. |
| 5xx·연결 실패 | 확인 단계 위, 버튼 `다시 시도하기` | 처리 중 문제가 발생했어요. 입력한 내용은 그대로예요. 잠시 후 다시 시도해 주세요. |
| 취소 확인(입력을 바꾼 뒤) | 대화상자, 버튼 `취소하기` / `계속 고치기` | 고친 내용이 사라져요. 취소할까요? |

- 오류 문구마다 "입력한 내용은 그대로예요"를 넣은 것은 정의서 2.1절이 입력값 보존을 정했기 때문이다. 구현이 값을 유지하지 않는다면 이 문장을 빼야 한다(7장).
- 같은 요청이 이미 저장됐는데 응답을 못 받은 경우(정의서 7장 #14)는 서버가 `unchanged`를 성공으로 돌려주므로 3.1의 성공 문구가 보인다. 별도 오류 문구는 없다.
- 취소 대화상자의 버튼을 "예/아니요" 대신 결과가 보이는 말로 썼다.

## 4. 관리자 화면: 수정 불가 사유

버튼은 비활성으로 두고, 버튼 가까이에 아래 한 줄을 항상 글자로 보인다. 호버 `title`만으로 두지 않는다.

| 대상 | 문구 |
|---|---|
| 탈퇴 회원 | 탈퇴한 회원이라 고칠 수 없어요. 개인정보가 이미 지워졌어요. |
| 가입 마무리 전 회원 | 아직 가입을 마무리하지 않은 회원이에요. 가입을 마친 뒤에 고칠 수 있어요. |
| 이메일 인증 상태를 못 읽음 | 가입 상태를 확인하지 못했어요. 잠시 후 화면을 다시 열어 주세요. |
| 운영자 계정 | 운영자 계정은 이 화면에서 고칠 수 없어요. 필요하면 개발 담당에게 요청해 주세요. |
| 가입 이메일 없음(비정상 데이터) | 가입 이메일이 없어 본인 확인을 할 수 없어요. 개발 담당에게 알려 주세요. |

- "가입 마무리 전" 이유는 상단 노란 안내(`signup-verify-password-copy.md` 5장)와 겹친다. 정의서 7장 #2대로 이 줄은 버튼 옆에만 둔다.
- 가입 마무리 전 회원 안내 5장 보조 줄에 아래 문장을 덧붙일 수 있다. 정의서 11장이 말한 "가입을 마친 뒤 이 화면에서 고칠 수 있다"는 연결이다: `가입을 마친 뒤에는 [이름·연락처 수정]으로 이름과 연락처를 고칠 수 있어요.`
- 운영자 계정과 이메일 없음은 이유 뒤에 "다음에 할 일"을 붙였다. 이 화면에서 해결할 수 없어서 막다른 길로 느껴지지 않게 하려는 것이다.

## 5. 관리자 화면: 정보 수정 이력

위치: 회원 상세 맨 아래, 수료 이력 아래.

| 위치 | 문구 |
|---|---|
| 섹션 제목 | 정보 수정 이력 |
| 표 머리 | 일시 / 처리한 관리자 / 바뀐 항목 / 고친 이유 / 메모 |
| 바뀐 항목 값 | 이름 / 휴대전화 / 이름, 휴대전화 |
| 고친 이유 값 | 회원 요청 / 오기 정정 / 가입 때 다른 사람이 입력한 값 정정 / 기타 |
| 메모 없음 | - |
| 탈퇴한 관리자 | (탈퇴) |
| 빈 상태 | 수정한 적이 없어요. |
| 더 보기 버튼 | 더 보기 |

- 빈 상태는 정의서 초안 그대로 두었다. 이력은 해결할 일이 없는 화면이라 "무엇이 없는지"만 말하면 충분하다.

## 6. 회원에게 보내는 안내 메일 (`profile_changed`)

대상: 저장 성공 뒤 가입 이메일. 변경이 없거나 탈퇴 회원에게는 보내지 않는다.

### 6.1 제목

**[바라 평생교육원] 회원 정보가 바뀌었어요**

| 옵션 | 문구 | 뉘앙스 |
|---|---|---|
| A (권장) | [바라 평생교육원] 회원 정보가 바뀌었어요 | 기존 제목(`가입을 마무리해 주세요`, `비밀번호 재설정 안내`)처럼 말 걸듯 쓴다. 바뀌었다는 사실이 한눈에 보인다. |
| B | [바라 평생교육원] 회원 정보 변경 안내 | 정의서·요청에 쓴 정식 이름. 딱딱하지만 검색·분류에 좋다. 본문에서 이 말을 쓴다. |
| C | [바라 평생교육원] 회원 정보가 수정됐어요 | 정의서 초안. "수정됐어요"는 수동형이라 누가 했는지 흐려진다. |

- 기능 이름 "회원 정보 변경 안내"는 B다. 받는 사람이 위험을 바로 알아차리게 A를 권한다. 제목은 짧아서 두 가지를 겸하기 어렵다. 어느 것이든 스팸함에 가지 않게 "바라 평생교육원"이 앞에 오는 형식은 유지한다.

### 6.2 본문

기존 `ses.ts` 템플릿 순서(인사, 문단, 링크, 문의처, 서명)에 맞춘 완성 모양이다.

```
안녕하세요. 바라 평생교육원이에요.

회원님의 정보가 바뀌어서 알려 드려요.
고객센터에서 회원님의 정보를 고쳤어요.

바뀐 항목: {이름 / 휴대전화 / 이름, 휴대전화}
바뀐 시각: {2026년 11월 26일 오후 2시 12분}

바뀐 내용은 개인정보를 지키기 위해 이 메일에 적지 않았어요.
회원님이 고객센터에 전화해서 요청한 것이 맞다면 따로 하실 일은 없어요.

본인이 요청하지 않았다면 전화로 알려 주세요.
전화: 010-9025-5093
운영시간: 평일 10:00~18:00(점심 11:30~13:00 제외)

바라 평생교육원
```

텍스트 메일(`text`)도 같은 순서와 줄 바꿈을 쓴다. 현재 템플릿이 만드는 HTML에서는 각 줄이 `<p>`가 된다.

- 항목명과 시각만 넣는다. 이전·새 값은 넣지 않는다(결정 Q7).
- 시각은 서버가 `Asia/Seoul` 기준으로 만들어 넣는다. 저장 성공 시각이다. 서머타임이 없어 표기가 단순하다.
- 항목명은 `changed` 배열을 "이름", "휴대전화", "이름, 휴대전화" 중 하나로 만든다. 연락처를 비운 경우도 항목명은 "휴대전화"이며 비웠다는 사실은 쓰지 않는다.
- "고객센터에서 회원님의 정보를 고쳤어요"는 가입 마무리 때 다른 사람이 입력한 값을 바로잡은 경우에도 사실과 맞다. "회원님이 요청했어요"로 단정하지 않고, 요청이 맞다면이라고 조건으로 썼다.
- "본인이 요청하지 않았다면 전화로 알려 주세요"는 요청받은 문장 그대로 두었다. "바로 연락해 주세요"(정의서 초안)는 시니어에게 재촉하는 느낌이라 뺐다.
- 링크는 넣지 않는다. 이 메일이 링크를 누르게 하면 피싱과 구분이 안 된다. 로그인 링크도 필요 없다.
- 비밀번호를 바꾸라는 말은 넣지 않는다. 이름·연락처 변경은 비밀번호와 관계가 없어서 불필요한 불안을 만든다.

본문 둘째 문단 옵션

| 옵션 | 문구 | 뉘앙스 |
|---|---|---|
| A (권장) | 회원님이 고객센터에 전화해서 요청한 것이 맞다면 따로 하실 일은 없어요. | 정상 상황을 먼저 안심시킨다. 기본 경로가 전화라서 사실이다. |
| B | 본인이 요청한 변경이라면 이 메일은 무시하셔도 돼요. | 짧다. "무시"는 이미 인증 메일에서 쓴 말이라 일관된다. 전화 요청이라는 단서가 없어 덜 구체적이다. |

### 6.3 구현 때 알아 둘 점 (backend-developer에게)

- 지금 `MailMessage`는 `link`가 필수고 `Template`은 고정 문장 배열이다. 이 메일은 링크가 없고 바뀐 항목·시각이 변수다. `link`를 선택으로 바꾸거나, 이 템플릿만 다른 조립 함수를 쓰는 방법 중 하나를 정해야 한다(정의서 8장이 같은 확인을 요청함).
- 링크가 없으면 HTML에서 `<p><a href=...>` 줄과 텍스트에서 링크 줄이 비어 보이지 않게 조립해야 한다.
- 메일 본문 테스트(`ses.test.ts`)에 "값이 본문에 없다"와 "전화·운영시간이 있다"를 넣는다.
- 문구가 길어서 인사 줄과 둘째 줄이 겹쳐 읽힌다면 "회원님의 정보가 바뀌어서 알려 드려요."를 뺀다. 의미가 사라지지 않는다.

## 7. 전화 응대 스크립트 보강 (운영자용)

`signup-verify-password-copy.md` 6장의 스크립트에 이어 붙이는 두 번째 스크립트다. 회원 화면에는 보이지 않는다.

운영시간: `{siteConfig.supportHours}` (현재 평일 10:00~18:00, 점심 11:30~13:00 제외). 운영시간 밖의 전화는 메시지를 남기게 하고 다음 운영시간에 처리한다.

정보 수정 요청이 왔을 때

1. 인사와 상황 확인: "바라 평생교육원입니다. 이름이나 휴대전화를 바꾸고 싶으신 거죠?"
2. 가입 이메일 확인: "가입하신 이메일 주소를 불러 주시겠어요?"
3. 일치 확인: 관리자 회원 상세에서 그 이메일의 회원이 있는지만 본다. 이름과 연락처는 묻지 않고 확인 기준으로 쓰지 않는다. 이메일이 맞으면 4번, 아니면 아래 "확인이 안 될 때".
4. 고칠 값 확인: "바꾸실 이름을 말씀해 주세요." (휴대전화도 같은 방식으로.) 받아 적은 값을 그대로 되읽는다: "홍길동으로 바꾸는 게 맞으실까요?"
5. 고치는 이유 확인: 대부분 "회원 요청"이다. 가입 때 다른 사람이 입력한 값이 의심되면(가입 마무리 전 재설정 메일로 가입을 마친 회원 등) 그 이유를 고른다. 이유를 회원에게 묻지는 않는다.
6. 화면에서 수정: `[이름·연락처 수정]`을 열고 값을 입력, 이유를 고르고 본인 확인에 체크한 뒤 `[변경 내용 확인]`을 누른다. 확인 단계의 큰 글씨 이름을 회원에게 다시 읽어 준다: "바뀌는 이름은 홍길동입니다. 맞으실까요?" 맞으면 `[저장]`.
7. 안내: "고쳤습니다. 가입하신 이메일로 안내 메일이 가요. 메일에는 어떤 항목이 언제 바뀌었는지만 적혀 있고, 바뀐 내용은 적혀 있지 않아요."
8. 영향 안내(확인 단계 경고가 있었을 때만): 입금 대기 신청이 있으면 "입금하실 때 이전 이름으로 하셔도 확인해 드릴게요." 수료 이력이 있으면 "수료증은 바뀐 이름으로 보여요. 이미 종이나 파일로 받으신 수료증은 이름이 다를 수 있어요."
9. 마무리: "다른 궁금한 점은 없으세요? 감사합니다."

확인이 안 될 때
- 이메일을 모르거나 회원 상세와 맞지 않으면 수정하지 않는다: "가입하신 이메일을 확인하신 뒤에 다시 전화 주시겠어요? 이메일을 확인하면 바로 도와 드릴게요." 이유를 길게 설명하거나 이름·연락처를 대신 대 보게 하지 않는다.
- 가입 마무리 전 회원: "아직 가입이 끝나지 않으셨어요. 가입을 마치면 바로 고쳐 드릴 수 있어요." 가입을 마무리하는 방법은 6장 스크립트로 이어 안내한다.
- 탈퇴한 회원: "탈퇴하신 계정이라 고칠 수 없어요. 다시 이용하시려면 새로 가입해 주세요."
- 주소나 사진을 바꾸고 싶다는 요청: "주소와 사진은 마이페이지의 신청 정보 수정에서 직접 바꾸실 수 있어요." 관리자가 대신 고치지 않는다.
- 이메일을 바꾸고 싶다는 요청: 이 기능으로는 바꿀 수 없다. "이메일은 지금 바로 바꿔 드리기 어려워요. 담당자에게 전달하고 안내해 드릴게요." 요청을 받아 적고 담당자에게 넘긴다(정의서 12장 후속 과제).
- 이전 값이 틀린 채 저장됐다고 회원이 알려 올 때: 값을 다시 확인해 한 번 더 수정한다. 이력에 한 건으로 남는다.

운영자가 지킬 점
- 이름과 휴대전화를 확인 기준으로 쓰지 않는다. 이메일 주소만 확인한다.
- 메모에 이름·전화번호·이메일을 적지 않는다. 시스템이 거절한다.
- 저장 뒤 회원에게 안내 메일이 간다고 꼭 말한다. 본인이 요청하지 않은 변경을 진짜 주인이 알아차리는 유일한 장치다.
- 메일이 갔다고 단정하지 않는다. 화면에 "안내 메일을 보내지 못했을 수 있어요"가 보이면 전화로 변경 사실을 한 번 더 알린다.
- 회원이 전화번호로 문자나 알림이 간다고 오해하면 바로잡는다. 지금 문자·알림톡 발송 기능은 없다.

## 8. 마이페이지 안내 문구 다듬기

위치: `app/(user)/my/page.tsx` 346행 근처. 현재 문구: `이름·이메일·휴대전화 변경은 고객센터로 문의해 주세요.`

기능 범위는 이름·휴대전화 수정이다. 이메일 변경은 범위 밖이고, 전화 본인 확인 기준이라 약속하지 않는다. 그래서 문구를 이름·휴대전화와 이메일로 나눈다.

| 옵션 | 문구 | 뉘앙스 |
|---|---|---|
| A (권장) | 이름과 휴대전화를 바꾸려면 고객센터로 전화해 주세요. 가입한 이메일 주소를 말씀해 주시면 바로 도와 드려요. 전화 `{siteConfig.phone}` / 운영시간 `{siteConfig.supportHours}` | 할 일(전화), 준비물(가입 이메일), 연락처가 한곳에 있다. 시니어가 다른 화면을 열지 않아도 된다. 이메일에 대해서는 말하지 않는다. |
| B | 이름과 휴대전화는 고객센터에서 고쳐 드려요. 전화 `{siteConfig.phone}` (`{siteConfig.supportHours}`). 이메일 변경은 같은 번호로 문의해 주세요. | 이메일까지 한 번에 다룬다. "바로 고쳐 드려요"는 이메일 변경이 약속처럼 들릴 수 있어 이메일을 문의로만 돌렸다. |
| C | 이름·이메일·휴대전화 변경은 고객센터(`{siteConfig.phone}`)로 문의해 주세요. | 기존 문구에 번호만 넣었다. 가장 짧지만 무엇을 준비해야 하는지 없다. |

- 권장 A. 이메일 변경을 마이페이지에서 안내해야 한다면 B를 쓰거나 A 뒤에 `이메일 변경은 문의해 주세요.`를 한 줄 더하는 안이 있다. 이메일 변경을 지원할지는 정의서 12장 후속 과제라 대표 확인 후 정한다.
- 전화번호는 `tel:` 링크로 만들어 모바일에서 바로 걸 수 있게 한다.
- 운영시간 밖 보조 한 줄(선택): `운영시간이 아니면 다음 운영시간에 처리해요.`
- 주소·사진은 같은 화면에서 직접 고칠 수 있으므로 이 문구에 넣지 않는다.
- 기존 문구가 있는 곳이 이름·이메일·휴대전화 읽기 전용 칸 아래라면, A로 바꿀 때 이메일 칸 아래에는 `이메일 변경은 문의해 주세요.` 한 줄을 따로 둘 수 있다.

## 9. 화면 한눈에 (문구 위치표)

## 10. 확인이 필요한 것

- Q4(수료증 외부 발급 여부와 재발급)는 대표 답을 기다린다. 2장의 수료증 안내는 그 답과 상관없이 쓸 수 있다. 외부 발급이 있고 재발급을 해 주기로 하면 7장 8번 응대 문구를 "재발급해 드릴 수 있어요"로 바꾼다.
- 3.3의 "입력한 내용은 그대로예요"는 frontend-developer가 서버 액션이 입력값을 보존하도록 구현할 때만 사실이다.
- 6장 메일은 `link` 필수 구조와 맞지 않는다(6.3). 템플릿 구조 결정이 필요하다.
- 처리방침 제위탁 표의 Amazon SES 업무는 "회원가입 인증·비밀번호 재설정 메일 발송"으로 한정돼 있다. "회원 정보 변경 안내" 메일이 이 범위에 들어가는지는 privacy-security-officer가 배포 전에 검토한다(결정 Q7 조건).
- 8장 옵션 A와 B 선택, 이메일 변경 안내 여부는 대표 또는 service-planner 확인.
- 이 문서는 문구만 확정한다. 정의서 10장 초안과 다른 곳은 이 문서가 우선한다(바뀐 곳: 메일 제목·본문, 성공 문구에 메일 사실 추가, 사유 3번 라벨, 도움말 어미, 입금 대기 경고 분리, 수정 불가 이유 보강, 이력 표 머리).
