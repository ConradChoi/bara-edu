# 관리자 2단계 인증(TOTP) 설계 점검 (구현 전)

- 점검일: 2026-11-26
- 점검: privacy-security-officer
- 대상: `docs/02-design/features/bara-edu-lms.admin-totp.md` (대표 결정 Q1~Q6 확정본). 기획서는 고치지 않았다(디자이너·카피라이터 병행 편집 중).
- 함께 본 코드: `api/src/auth/{routes,service,sessions}.ts`, `api/src/http/{guard,logging}.ts`, `api/src/ops/routes.ts`, `api/src/query/routes.ts`, `proxy.ts`, `api/db/02-schema.sql`(접속 기록 정리 작업), 처리방침 `docs/01-plan/features/bara-edu-lms.legal-privacy.md`
- 선행 점검: 비밀번호 찾기 점검 I-1~I-3(`bara-edu-lms.password-reset-request.md`). 이 기능은 I-3(메일함 장악 = 관리자 장악)의 후속이다.
- 법률 자문이 아니다. 법 조항 해석은 "변호사 검토 필요"로 표시했다.

## 판정: 조건부 승인

설계의 뼈대는 맞다. 세션 발급 시점(API login)과 세션 확인 시점(API guard)에 2단계를 함께 거는 구조라, 앱 화면(proxy)을 건너뛰고 쿼리 API(`/v1/query`)나 ops(`/v1/op/:name`)를 바로 불러도 guard가 `userId=null`을 주므로 관리자 권한이 나오지 않는다. 메일로 2단계를 해제하는 경로가 없는 점, 재설정이 `mfa-fail`을 지우지 않는 점, 재등록에 전화로 받는 등록 코드를 요구하는 점(Q1)도 위협 모델에 맞다.

치명적(Critical) 이슈는 없다. 다만 아래 주요(Important) 8건은 **API 계약을 확정하기 전에 설계에 반영해야 한다**(구현 뒤에 고치면 스키마·흐름이 바뀐다). 반영 여부는 backend-developer가 API 계약 문서에 적고, qa-reviewer가 테스트로 고정한다. 배포 게이트는 맨 아래 표에 있다.

## 1. 2단계 없이 관리자 권한을 얻는 경로 점검

| 경로 | 결과 | 근거 |
|---|---|---|
| 도입 시점의 기존 세션 | **구멍 있음 (I-1, I-2)** | 유예 기간(`optional`)에는 guard 규칙이 꺼져 있어 비밀번호만으로 만든 30일 세션이 계속 살아 있고, 그 세션으로 입구 A 등록까지 할 수 있다 |
| 2단계 대기표 | 대체로 안전 | 32바이트, 해시 저장, 5분, 1회용, 쿠키 전달. 보완은 M-2(대기표·등록 대기·등록 코드 묶기) |
| 세션 guard(`mfa_at`) | 안전, 단 수명 규칙 보완 필요 (I-2) | `role='admin' and mfa_at is null`이면 세션 없음. 가입 마무리(`signup-link/complete`) 세션, 승격, 앞으로 생길 발급 경로를 모두 막는다 |
| 재설정 | 안전 | 재설정은 세션만 지우고 2단계는 그대로. 다음 로그인에 6자리 필요 |
| 재등록·등록 코드 | **유예·롤백 모드에서 구멍 (I-1)**, 휴대폰 분실 뒤 재등록 경로가 정의되지 않음 (I-4) | 아래 참고 |
| 다른 관리자의 초기화 | 안전(내부자 위험은 받아들임) | 초기화하는 관리자의 6자리 재확인, 전화 확인, 기록 롤백. 초기화한 관리자가 등록 코드를 알게 되므로 "관리자 A 세션 + B의 메일함"이면 B를 가져갈 수 있다. 소수 관리자 구조에서는 받아들일 수 있고, 알림(I-6)으로 사후에 알아챌 수 있게 한다 |
| CLI 복구 | 안전(서버 접근 권한자 = 이미 최고 권한) | 보완은 M-5 |
| 서비스 키 API 경로 | 안전 | guard가 모든 요청에서 서비스 키를 확인한 뒤 세션을 푼다. `access:'service'` ops 6개(`admin-diagnosis`, `admin-profile`, `enrollments`, `enrollments-approve`)도 `userId`가 필요하고(`ops/routes.ts` 13행) 안에서 role을 확인하므로, guard가 `userId=null`을 주면 함께 막힌다. 서비스 키만 있고 세션이 없으면 anon 권한뿐이다. **새 MFA 키는 API(EC2)에만 두고 Amplify 환경 변수에는 넣지 않는다**(앱은 이 키가 필요 없다) |
| proxy | 안전(방어선 아님) | proxy는 화면 이동만 막는다. 실제 권한은 guard가 정한다. 변경 필요 없음. 관리자 쿠키 만료는 API의 `expiresAt`을 그대로 쓰면 된다(`withRefreshedCookie`는 `renewed`일 때만 다시 쓴다. 관리자 세션은 연장하지 않으므로 그대로 맞는다) |
| 운영 모드 설정 | **실패 시 열림(fail-open) 위험 (I-3)** | `ADMIN_MFA_MODE`가 빠지면 어떤 값이 되는지 정하지 않았다 |

## 2. 발견 사항

### 주요(Important): API 계약 확정 전 설계 반영

| # | 이슈 | 기획서 위치 | 근거 | 권장 조치 |
|---|---|---|---|---|
| I-1 | **유예(`optional`) 모드와 강제 뒤 `optional` 롤백에서, 초기화된 계정이 등록 코드 없이 다시 등록된다.** `optional`에서는 미등록 관리자가 비밀번호만으로 세션을 받고 입구 A로 등록할 수 있다. 유예 중 다른 관리자가 초기화한 계정, 또는 강제 뒤 버그로 `optional`로 되돌렸을 때 초기화 상태인 계정은 메일함만 가진 공격자가 재설정 → 로그인 → 입구 A로 **자기 인증 앱을 먼저 등록**할 수 있다. 이 등록은 강제 모드로 돌아와도 정상 등록으로 남는다. (b) 7.3 롤백 표에 "`optional`로 되돌려도 초기화된 계정은 등록 코드가 필요"를 적는다. (c) 유예 중 등록 확정 때 `mfa_enrolled` 알림을 다른 관리자에게도 보낸다(I-6) |
| I-2 | **도입 전 세션과 입구 A로 "승격"된 세션이 30일 수명을 그대로 갖는다.** 유예 기간 동안 guard 규칙이 꺼져 있고, 입구 A는 비밀번호만으로 만든 현재 세션에 `mfa_at`을 채운다(3.4 끝). 이 세션은 30일 슬라이딩 세션이라 강제 뒤에도 12시간 제한을 받지 않는다. 또 유예 시작 전부터 살아 있던 세션(예: 예전에 재설정으로 얻은 공격자 세션)도 입구 A로 등록해 영구 권한을 얻을 수 있다 | 2.3 관리자 세션 기간, 3.4 입구 A, 5.4, 7.1 단계 1·3 | 안전성 확보조치 기준 제6조(접근통제), 보안 설계 | (a) 유예 시작(`optional` 배포) 직후 **모든 관리자 세션을 일괄 삭제**한다. 유예 중 등록하려면 다시 로그인해야 한다. (b) 입구 A는 기존 세션에 `mfa_at`을 채우지 말고, 등록 확정 때 **그 세션을 지우고 새 관리자 세션(12시간)을 발급**한다. (c) 관리자 세션 수명은 발급 시각이 아니라 `resolveSession`에서 매번 판정한다: `role='admin'`이면 `min(created_at + 12h, last_seen_at + 1h)`을 넘긴 세션은 지운다. `optional`·`off`를 포함해 모든 모드에 적용한다. 관리자 세션에는 슬라이딩 연장(`sessions.ts` 30~37행)을 하지 않는다 |
| I-3 | **`ADMIN_MFA_MODE`의 기본값이 정해지지 않았다.** 값이 빠지거나 오타가 나서 `off`로 해석되면 아무도 모르게 보호가 꺼진다(실패 시 열림). `off` 전환을 적어 두는 곳도 사람의 운영 기록뿐이다 | 7.1, 7.3, 9.1 `config.ts` | 보안 설계(안전한 기본값) | (a) 운영(`NODE_ENV=production`)에서 값이 없거나 세 값 중 하나가 아니면 **시작을 거절**한다. (b) 강제 뒤에는 운영 기본값을 `enforce`로 바꾼다. (c) API가 시작할 때 모드를 서버 로그에 남기고, `enforce`가 아니면 매 시작마다 경고 로그와 관리자 화면 배너("2단계 인증이 꺼져 있어요")를 띄운다. (d) `off`·`optional`로 바꿀 때는 대표 승인과 시각을 운영자 접근 기록 문서에 적는 것을 7.3에 의무로 적는다 |
| I-4 | **휴대폰을 잃은 관리자가 복구 코드로 로그인한 뒤 새 휴대폰을 등록하는 방법이 없다.** 입구 C는 "지금 휴대폰의 6자리"를 요구하는데(2.4, 3.4), 2.7.1과 3.3은 복구 코드 로그인 뒤 `/admin/security`에서 새로 등록하라고 안내한다. 구현자가 이 틈을 "세션만으로 교체 허용"으로 메우면, 세션을 훔친 사람이 인증 앱을 자기 것으로 바꿔 계속 권한을 갖게 된다 | 2.4 입구 C, 2.7.1, 3.3 성공, 3.4 끝, 4.4 `enroll/start` | 보안 설계(재확인 누락) | 인증 앱 교체의 재확인 수단을 "지금 인증 앱의 6자리 **또는** 아직 쓰지 않은 복구 코드 1개(이 확인으로 소모)"로 정한다. 세션만으로는 교체할 수 없다. `enroll/start`의 세션 요청을 `{ currentCode? , recoveryCode? }` 중 하나 필수로 바꾸고, 실패는 `mfa-fail`로 센다. 복구 코드가 0개인 세션은 교체할 수 없고 다른 관리자의 초기화를 안내한다 |
| I-5 | **마스터 키를 교체하면 복구 코드 HMAC을 다시 계산할 수 없다.** 2.6은 "새 키로 다시 암호화하는 일회성 명령"으로 교체한다고 했지만, 복구 코드는 원문이 없어 새 하위 키로 HMAC을 다시 만들 수 없다. 키를 바꾸는 순간 모든 복구 코드가 맞지 않게 되고, 단일 관리자 상황에서는 잠김으로 이어진다 | 2.4 복구 코드 저장, 2.6 하위 키·키 교체, 2.11 `mfa_recovery_codes` | 보안 설계(키 관리) | `mfa_recovery_codes`(그리고 HMAC으로 바꿀 경우 `mfa_enroll_tickets`, M-3)에도 `key_version` 컬럼을 둔다. 검증 때 행의 버전 키로 계산한다. 옛 키는 그 버전의 복구 코드가 모두 쓰이거나 재발급될 때까지 읽기용으로 남긴다. 교체 명령이 끝나면 "옛 버전 행 수"를 출력하고, 0이 되면 옛 SSM 파라미터를 지운다. HKDF `info`에 용도와 버전을 함께 넣는다(`bara-mfa/totp-secret/v1`). 교체 주기: 정기 교체는 연 1회, 유출이 의심되면 즉시(이 문서로 정한다) |

(b) 관리자 대시보드에 "최근 7일 보안 이벤트"(잠김·복구 코드 사용·등록·초기화·재설정) 카드를 둔다. 데이터는 `admin_access_logs`에 이미 있다. (c) 관리자 계정의 `비밀번호재설정` 기록도 같은 경로로 알린다 |
| I-7 | **계정 한도(10회/15분)만으로는 오래 끄는 추측 공격을 막지 못한다.** 비밀번호를 아는 공격자는 하루 960번 시도할 수 있고, ±1칸 허용으로 한 번에 맞는 번호가 3개라 한 번 성공 확률이 약 3/1,000,000이다. 하루 약 0.29%, 30일 약 8%, 1년 약 65%다. 2.9의 "무시할 수준"은 15분 기준으로만 맞다. 잠김 알림은 I-6 때문에 공격자에게 간다 | 2.9 계정당·부작용 문단 | 안전성 확보조치 기준 제5조(인증 실패 시 접근 제한, 조문 번호는 변호사·법령정보센터 확인), 보안 설계 | (a) 2단 한도를 둔다: 15분 10회(지금 그대로) + **24시간 30회**. 24시간 한도에 걸리면 24시간 잠그고, `2단계인증잠김 limit=daily` 기록, I-6 경로로 다른 관리자·운영 주소에 알린다. `rate_events` 보관이 25시간이라 24시간 창을 그대로 쓸 수 있다. (b) 잠긴 계정을 풀어 주는 수단을 CLI `mfa-unlock --email`(접속 기록 포함)로 둔다. (c) 6자리 재확인(초기화, 복구 코드 재발급, 입구 C)의 실패도 같은 `mfa-fail`로 센다(4.5·4.6에 명시) |
| I-8 | **강제 전 점검(`mfa-report`)이 "등록된 인증 앱이 진짜 본인 것인가"를 확인하지 않는다.** 유예 중 공격자가 먼저 등록하면(I-1, I-2), "등록 완료·6자리 로그인 성공"이 그대로 통과한다 | 7.1 단계 2, 7.2 | 보안 설계(도입 절차) | `mfa-report`에 관리자별 등록 일시·등록 IP·`via`와 최근 로그인 IP를 출력하고, 대표가 각 행을 "본인이 등록함"으로 확인한 뒤 강제한다. 유예 중 `already_enrolled`(5.2)가 본인이 등록하지 않은 계정에서 나오면 **사고로 처리**한다(즉시 CLI 초기화 + 비밀번호 재설정)는 문구를 7.2에 넣는다 |

| M-2 | 대기표·등록 대기·등록 코드를 어떻게 묶는지 계약에 없다 | 2.2, 2.4, 4.4 | `enroll/confirm`은 `enrollment.user_id = challenge.user_id`(또는 세션 사용자)와 `enrollment.challenge_hash = 이 대기표`를 확인한다. 등록 코드는 `start`에서 "확인됨, 이 enrollment에 묶임"으로 표시하고 `confirm`과 같은 트랜잭션에서 `used_at`을 찍는다. `verify`는 role뿐 아니라 "지금도 등록돼 있는가"와 운영 모드도 다시 확인한다. 대기표의 `purpose`가 다르면 거절한다(4.2에 이미 있음) |
| M-3 | 등록 코드 8자리(1억 가지)를 SHA-256으로만 저장하면 DB가 새는 순간 몇 초 만에 원문이 나온다 | 2.7.2, 2.11 `mfa_enroll_tickets.code_hash` | 복구 코드처럼 HKDF 하위 키(`enroll-ticket`)로 만든 HMAC으로 저장한다(I-5의 `key_version` 포함). 대기표(32바이트 무작위)는 SHA-256 그대로 괜찮다 |
| M-4 | 암호문의 AAD가 `user_id`+버전뿐이라 `mfa_enrollments`의 암호문을 `mfa_factors`로 옮겨도 풀린다 | 2.6 암호화 | AAD에 용도(`factor`/`enrollment`)를 넣거나, 등록 확정 때 새 IV로 다시 암호화한다. IV는 행마다 12바이트 무작위면 충분하다(이 규모에서는 충돌 위험 없음). 같은 IV를 다시 쓰는 코드 경로가 없게 한다(재암호화 때도 새 IV) |
| M-5 | CLI 실행 흔적이 사람의 기록에만 의존한다 | 2.7.3 | 운영 서버 접속은 SSM Session Manager로만 하고 세션 기록(CloudTrail·세션 로그)을 켠다. CLI는 `mfa-ticket`을 이미 등록된 계정에는 거절하고, `--reason`은 정해진 키만 받는다. 등록 코드 출력은 터미널에만 하고, Session Manager 세션 로그에 등록 코드가 남지 않게 출력 직전에 경고하거나 로그 기록을 끄고 실행한다(운영 문서에 적는다) |
| M-6 | 운영에서 `BARA_MFA_KEY`(평문 환경 변수)로도 시작할 수 있게 읽힌다 | 2.6 마스터 키 | 운영에서는 `BARA_MFA_KEY_PARAM`(SSM)만 허용하고 `BARA_MFA_KEY`가 있으면 시작을 거절한다. 키는 base64를 풀었을 때 정확히 32바이트여야 한다. 시작 시 검증용 값(5.3)은 `auth.mfa_key_check(key_version, ciphertext)` 한 행으로 두고 버전마다 만든다 |
| M-7 | 마스터 키 오프라인 사본 여부가 미정이다 | 7.2 | **사본을 두지 않는다.** 잃어도 CLI로 전원 재등록하면 복구되고(관리자 소수), 사본은 유출 경로만 늘린다. 대신 SSM 파라미터 삭제 방지(IAM에서 `ssm:DeleteParameter` 거부)와 KMS 키 삭제 대기 기간을 운영 문서에 적는다 |
| M-8 | 세션이 "복구 코드로 들어왔는가"를 기억할 칸이 없다(4.5 `signedInWithRecovery`) | 2.11 `auth.sessions` | `auth.sessions.mfa_method text check (mfa_method in ('totp','recovery','enroll'))`를 추가한다 |
| M-9 | 재사용 응답을 실패로 세지 않는 규칙이 오라클이 되지 않게 범위를 정해야 한다 | 2.8 거절 응답 | "재사용"은 지금 ±1칸 안에서 맞는 칸이 `last_used_step` 이하인 경우로만 한정한다. 과거 칸 전체를 뒤져 판정하지 않는다. TOTP 비교는 칸마다 상수 시간 비교, 루프는 3칸을 모두 돈다 |
| M-10 | 처리방침 제8조 5호는 접속 기록을 "보관한 지 1년이 지난 기록만 자동으로 파기"한다고 적었는데, DB 정리 작업은 2년 지난 기록을 지운다(`02-schema.sql` 1759행). 이번 기능으로 접속 기록이 늘어나므로 함께 맞춘다 | 6장, 처리방침 제8조 | 처리방침 v8 문구를 "2년이 지난 기록만"으로 고친다(DB 쪽이 더 보수적이므로 DB를 바꾸지 않는다) |
| M-11 | 복구 코드 [파일로 받기]를 서버 URL로 만들면 접근 로그·캐시에 남을 수 있다 | 2.4 단계 5 | 브라우저에서 Blob으로 만든다(서버 왕복 없음). 서버 액션 결과는 `no-store`, 복구 코드가 있는 상태를 콘솔·오류 추적에 넘기지 않는다 |

## 3. 비밀 키 저장 결론

- AES-256-GCM + 행마다 무작위 12바이트 IV + AAD(`user_id`, 버전, 용도) + SSM SecureString 마스터 키 + HKDF 용도별 하위 키: **승인**. KMS를 매번 부르지 않는 결정도 서비스 키와 같은 수준이라 받아들인다.
- 조건: I-5(복구 코드 키 버전), M-3, M-4, M-6, M-7.
- 키는 API 프로세스(EC2)에만 둔다. Amplify(앱) 환경 변수·빌드 로그에는 넣지 않는다. 앱 서버는 `otpauthUri`를 받아 QR만 그리므로 비밀 키가 앱 서버 메모리를 지나간다. 이 값을 Amplify SSR 로그(CloudWatch)에 남기지 않는 것을 qa-reviewer가 확인한다.

## 4. 재사용 방지·시도 제한·복구 코드 결론

- `last_used_step` + `for update`: **승인**. 로그인·재확인·등록 확인이 같은 행을 쓰므로 모든 경로에서 재사용이 막힌다.
- 복구 코드 약 50비트, HMAC 저장, 정규화 입력: **승인**. 1회용은 `update … set used_at = now() where user_id = $1 and code_hmac = $2 and used_at is null returning id`로 원자적으로 처리한다(조회 뒤 갱신 금지). 복구 코드 성공도 `mfa-fail` 예약을 푼다.
- 시도 제한: I-7 반영 조건으로 승인. IP 한도는 `x-bara-client-ip`가 있을 때만 걸리므로(`routes.ts` 53행 주석), 계정 한도가 실제 방어선이다.

## 5. 세션 12시간·1시간 미사용 vs 안전성 확보조치 기준

- 제6조의 "외부에서 개인정보처리시스템에 접속할 때 안전한 인증수단" 요건에 대해, 인증 앱의 일회용 비밀번호(TOTP)는 실무상 인정되는 수단으로 보인다. 적용 대상·예외는 **변호사 검토 필요**(기획서 질문 그대로).
- 자동 접속 차단: 이번 점검에서 검색으로는 현행 고시의 해당 항 번호와 문언을 확인하지 못했다. 제 이해로는 "일정 시간 이상 업무처리를 하지 않으면 자동으로 접속을 차단"하는 취지이고, 시간을 숫자로 정해 두지는 않는다. **조문 번호·문언은 국가법령정보센터 원문과 변호사로 확인한다.**
- 실무 판단: 최대 12시간(연장 없음) + 1시간 미사용 만료는 "일정 시간 미사용 시 차단"의 취지를 충족하는 수준으로 본다. 조건은 (1) I-2(c)대로 모든 관리자 세션에 매번 판정할 것, (2) M-1대로 "사용"을 관리자 작업으로 한정할 것, (3) 그 시간을 **내부 관리계획(접근통제)에 숫자로 적을 것**이다. 회원 정보를 대량으로 보는 화면이 늘어나면 30분으로 줄이는 것을 검토한다.
- 인증 실패 시 접근 제한(제5조 관련 항으로 알려져 있음, 번호 확인 필요): 대기표 5회 + 계정 15분 10회 + (I-7) 24시간 30회로 충족한다.

## 6. 기록 규칙

남긴다(`admin_access_logs`, 실패하면 함께 롤백):

| action | 결정 |
|---|---|
| `로그인` | **남긴다.** 2단계를 통과해 세션을 만들 때마다. detail `mfa=totp` / `mfa=recovery;left=n`, IP. 제8조 접속기록 취지에 맞고, 지금 비어 있는 관리자 로그인 기록을 채운다 |
| `2단계인증등록`, `복구코드재발급`, `2단계인증초기화`, `2단계인증등록코드발급`, `2단계인증잠김` | 기획서 2.10대로. `잠김`은 `limit=account` / `limit=daily`(I-7) |
| `2단계인증잠금해제` | 신규(I-7 CLI). `by=db;operator=…` |
| `로그아웃`(세션 만료 포함) | 남기지 않는다(필요 이상) |

서버 로그(구조화 로그, 접속 기록 아님):

- 개별 실패(잠김 전): `{ event: 'mfa_fail', userId, kind: 'wrong_code' | 'reused' | 'challenge_invalid' | 'ticket_invalid', ipKey }`. 입력한 값은 남기지 않는다.
- 시작 시 운영 모드와 로드한 키 버전 목록(키 값 아님).
- `off`·`optional`로 시작했다는 경고(I-3).

어디에도 남기지 않는다(서버·앱 로그, 오류 추적, 접근 로그, 접속 기록 detail, 메일):

- 6자리 번호, 복구 코드, 등록 코드, 대기표(`challengeToken`, `bara_mfa` 쿠키 값), 비밀 키(`secretBase32`), `otpauth://` 주소, QR SVG, 마스터 키·하위 키, SDK 오류 메시지 원문.
- 확인 방법: Fastify 기본 요청 로그는 본문을 남기지 않고 URL만 남긴다. 그래서 위 값은 **본문으로만** 받는다(4장 공통 규칙, 쿼리 금지 유지). 앞으로 헤더로 옮기면 `logging.ts`의 `SECRET_HEADERS`에 추가한다. qa-reviewer는 테스트에서 로그 스트림에 위 값이 하나도 없는지 확인한다(9.1 마지막 행).

## 7. 개인정보처리방침 개정 필요 여부

- **회원(정보주체)의 개인정보는 새로 처리하지 않는다.** 휴대폰 번호·기기 정보도 받지 않는다. 그래서 수집 항목·목적·보유 기간 표(제1~3조)는 바꿀 필요가 없다.
- 새로 처리하는 것은 관리자 계정(관리자도 회원 계정이다)의 인증 정보(암호화한 비밀 키, 복구 코드 HMAC, 사용 시각, 대기표 발급 IP, 로그인 접속 기록)다. 내부 직원의 인증·접속 정보가 처리방침에 들어가야 하는지는 **변호사 검토 필요**. 실무 권장은 아래 3가지를 **처리방침 v8에 함께 묶는 것**이다. 이번 기능만으로 별도 개정을 할 필요는 없다.
  1. 제8조에 한 항 추가: "관리자 접속 시 비밀번호와 일회용 인증번호(2단계 인증)를 함께 확인하고, 일정 시간 사용하지 않으면 접속을 자동으로 끊습니다." 사실과 맞추는 개정이고, 배포 뒤에 게시한다(배포 전에 게시하면 사실과 다르다).
  2. 제5조 Amazon SES 위탁 업무를 "회원가입 인증·비밀번호 재설정·회원 정보 변경 안내·계정 보안 알림 메일 발송"으로 넓힌다. 보안 알림 4종(I-6 포함)이 관리자(회원) 이메일로 SES를 거쳐 나간다.
  3. M-10(접속 기록 파기 시점 1년 → 2년) 바로잡기.
- 기획서 6장의 판단("필요 없다, 제8조 추가는 선택")과 같은 방향이다. 다만 2번 SES 문구는 메일이 실제로 나가므로 "선택"이 아니라 **v8에 넣는 것을 권장**한다.
- 처리방침과 별개로 **내부 관리계획은 반드시 고친다**(접근통제: 2단계 인증 대상·세션 시간, 초기화 절차 2.7, 마스터 키 관리 2.6, 잠금 해제 절차).
